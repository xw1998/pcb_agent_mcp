# 140 — 串扰多段求解的并行（`jobs`）

> 承接 `docs/139` 第 8 节的欠账 (2)：「串扰多段未并行」。本文只记这一件，版本 `0.0.149`。

## 1. 要修的是什么

`board_crosstalk` 会把两个网之间所有「平行、够近、够长」的候选段排成一列，`max_runs` 决定解几段。
每一段都是一整套独立的 2-D 场解（`calc/field2d.py`，两次 `_cap_modes`、四次网格求解）。这些解之间
**不共享任何东西**——不同宽度、不同间隙、不同板高，只是碰巧在同一条板上、在同一个调用里要算。

上一轮只做到「默认只解最近的一段」，把成本从"段数 × 5 min"压到"5 min"；多解的代价仍是**线性累加**。
这一轮把累加改成重叠。

## 2. 为什么能并行，以及为什么是进程不是线程

`solve` 是纯 Python 数值循环（红黑 SOR，数千次 sweep），GIL 会把它绑死，线程零收益。

每个 run 的参数是一个只含 `float/int/str` 的 dict（`kind / width_mm / spacing_mm / dielectric_mm /
length_mm / rise_time_ns / copper_um / er / amplitude_v / termination_ohm / mesh_div /
samples_per_delay / waveform_points`），结果也是纯 dict —— 天然可 pickle。

因此 `sim/couple.py` 里：

- `_solve_one_run(kw)` 是**模块级**函数（spawn 的 worker 要能找到它），负责一次求解并回填 `elapsed_s`；
- `_solve_runs(specs, jobs)` 用 `multiprocessing.get_context("spawn").Pool(jobs)` + `Pool.map`，
  **保序**，所以 `runs_solved` 的 rank 顺序与串行一致。

用 `spawn` 而不是 `fork`：Windows 上只有 spawn，而 `fork` 会把父进程的 LVGL/线程状态一起带进子进程，
求解这种"只吃参数"的活没有理由要那个副本。

## 3. 默认为什么是串行（这里推翻过一次设计）

第一版把默认设成 `auto = min(runs, cores, 8)`——用起来省事，但它是**库在调用方背后起进程**。
Windows 的 spawn 会重新导入 `__main__`：调用方的脚本如果没有 `if __name__ == "__main__":` 守卫，
每个 worker 都会把那个脚本从头再跑一遍。这不是性能问题，是"库把用户的程序执行了 N 次"。

于是默认改成 **`jobs=1`（串行）**，要并行必须显式说：

- `jobs=3`（数字），或
- `jobs="auto"` → `min(runs, cores, 8)`，或
- 机器级 `PCB_AGENT_JOBS=auto` / `PCB_AGENT_JOBS=3`（显式 `jobs` 仍优先）。

上限 8 与 `max_runs` 的上限一致：超过 8 段也没有 8 段可解。

## 4. 实测

`_par_probe.py`（未跟踪临时件）：3 段平行跑线 + 一层 B.Cu 地，`rise_time_ns=0.5, max_runs=3,
mesh_div=4, samples_per_delay=10, waveform_points=11`，8 核机器。

| 段 | 串行 `elapsed_s` | `jobs=3` 时 `elapsed_s` |
|---|---|---|
| rank 1（gap 0.3） | 75.33 | 117.76 |
| rank 2（gap 0.4） | 102.50 | 136.48 |
| rank 3（gap 0.45→被拒前的同宽段） | 146.24 | 143.57 |
| **wall（`value.parallel.wall_s`）** | **324.06** | **143.97** |

两件事一起说清楚：

1. **wall 从 324.1 s 降到 144.0 s（2.25×）**，下限是"最长的那一段"，不是"相加除以进程数"每个 run 的
   `elapsed_s` 自己变长了（75→118、102→136），因为三个求解在同 8 核上互相挤，同时算的数更慢。
   所以并行买到的是 **wall**，不是**算力**：段数再多，最慢那一段就是地板。
2. `value.parallel` 每次都写清楚发生了哪一种：`used`、`jobs`、`why`、`wall_s`、`asked`。
   `why` 在串行时是 `jobs=1: runs were solved one after another` 或
   `one run to solve: there is nothing to overlap`。

## 5. 答案必须一模一样

并行只允许改 wall clock，不允许改数字。**实解**上量过一次（`_par_probe2.py`，未跟踪：2 段平行、
`mesh_div=4`、`max_runs=2`）：串行 wall **318.2 s** 对 `jobs=2` **168.9 s**（1.88×），两次
`runs_solved` 的 `next`/`fext` **整段落逐字符相同**（两行分别 670 与 808 字符，含完整 `waveform_ns_v`）：

| | 串行 `jobs=1` | 并行 `jobs=2` |
|---|---|---|
| wall | 318.2 s | 168.9 s |
| rank 1 `next.peak_v` | 0.0166954 | 0.0166954 |
| rank 2 `next.peak_v` | 0.0146172 | 0.0146172 |
| 两段结果 JSON 逐字符 | — | 相同（670 / 808 字符） |

- `Pool.map` 保序 + 每个 run 参数完全独立 ⇒ 理论上同值；
- 一处连带改动：run 的参数现在以 **dict 关键字**传进 `_X.coupled_lines(**kw)`（这是 worker 能拿到的唯一形态），旧测试桩写的是位置参数 `(kind, width, gap)`，全量回归里被这一改动照出来 3 例红——桩改成 `(kind, width_mm, spacing_mm)` 即可，被测代码没有错，**是桩跟着调用形态走**；
- 测试里钉住：`TestHowManyRunsAtOnce::test_a_parallel_answer_is_the_same_answer`
  在一个**临时脚本文件**里跑（`python -c` 不行：spawn 的 worker 重导入的是 `__main__` 的
  **文件路径**，`-c` 没有文件，worker 里就看不到桩），把 `_X.coupled_lines` 在**模块级**打桩
  （这样 worker 也吃到），分别 `jobs=1` 与 `jobs=2` 各跑一次，断言两个 `next` 序列逐位相同且
  `parallel.used is True`、`parallel.jobs == 2`。这一例 1.6 s 内跑完，因为桩是算术。

## 6. 池起不来怎么办

`_solve_runs` 的 `except Exception` 不是"兜底不报"，而是**兜底并说明**：

```
why: "the worker pool could not be started (RuntimeError: ...), so the runs were
      solved one after another - the numbers are the same and only the wall clock pays"
```

测试 `test_a_pool_that_cannot_start_says_so_and_still_answers` 用
`mock.patch("multiprocessing.get_context", side_effect=OSError(...))` 把这条路径钉死。
在 pytest 里跑并行本来就会走到这条路径（`__main__` 是 pytest 自己），所以"在测试里看不到
`used=True`"**不是缺陷，是 spawn 的语义**——真正的并行由上面那个脚本文件用例覆盖。

## 7. `tools.py` 的广告

上一轮实现有 `max_runs`、schema 里却没有（调用方看不见的参数等于不存在）。这一轮补两处：

- `max_runs`：`solve this many of the ranked runs, each a whole field solve (default 1, cap 8)`
- `jobs`：`off by default, 'auto' = min(runs, cores, 8), cap 8`

描述里删掉两句过期的话："the field solve is run on the worst one only"（现在由 `max_runs` 决定）
与"this one solve took 285.8 s"（现在要说的是"每段都是一整套解，5 段就是 5 份"）。
