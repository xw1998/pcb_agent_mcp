# 占用/可通行表示 + 经验累积模块（补天联动）

日期：2026-10-27
承接 `01-AI原生的PCB表示.md`。本篇补两块：
**(A) 让 AI 知道"哪里被占、哪里走不过、元件具体在哪"**——不能只给密度百分比；
**(B) 让 AI 累积经验少犯同样的错**——装了补天走补天，没装走本地，两者不并存。

---

# A. 占用与可通行：从"密度数字"升级为"阻塞账本"

## A0. 为什么"密度 0.78"这种数字没用

密度只回答"挤不挤"，不回答模型真正要决策的三个问题：

1. **能不能改**？（U1 的 courtyard 是硬的，别人走过的 GND 线是可挪的）
2. **到底卡在哪一段**？（是整条走廊都过不去，还是只有一个 2mm 的隘口）
3. **放得下吗**？（给我一个 8×6mm 的模块，哪里能放）

⇒ 表示要做成 **可行动的（actionable）**：每条阻塞都带**归属对象 + 是否可变 + 影响哪个走廊**。

## A1. 阻塞物账本（核心）

```yaml
blockers:                       # 按对目标走廊的影响排序
  - id: B1
    kind: component_courtyard   # 器件占位（硬）
    ref: U1
    rect: {x: 9.2, y: 5.0, w: 6.4, h: 6.4, side: top, layers: [F.Cu]}
    mutability: fixed           # fixed | movable | reroutable | removable
    blocks: [ch_power_mcu]      # 它挡住了哪条通道
    why: "器件本体，不可移动（已锁定）"
  - id: B2
    kind: keepout               # 设计者明确禁区（硬）
    rect: {x: 36, y: 16, w: 10, h: 8, layers: [F.Cu, B.Cu]}
    mutability: fixed
    why: "RF 天线净空区（人为设定）"
  - id: B3
    kind: pour                  # 覆铜（可避让）
    net: GND
    rect: {x: 10, y: 18, w: 30, h: 11, layers: [B.Cu]}
    mutability: reroutable
    why: "GND 整层填充，布线时可按 clearance 让位"
  - id: B4
    kind: tracks                # 已布铜（可改层/可重布）
    nets: [VCC, 3V3]
    count: 24
    span: {x: 22, y: 6, w: 14, h: 4, layers: [F.Cu]}
    mutability: reroutable
  - id: B5
    kind: edge_clearance        # 板边安全带
    width: 0.5
    mutability: fixed
  - id: B6
    kind: mounting_hole
    at: [3.5, 3.5]
    keepout_r: 3.0
    mutability: fixed
```

**关键字段是 `mutability`**：`fixed` 的只能绕，`reroutable` 的可以谈。图像永远传达不了这个信息，而它直接决定 AI 下一步该"改布局"还是"改布线"。

## A3. 自由空间矩形分解（让"放得下吗"变成算术）

网格让模型"看个大概"，矩形分解让它**做判断**。从栅格算极大空矩形，很便宜：

```
FREE RECTS (F.Cu ∪ B.Cu 都空的区域, 按面积降序)
  F1  14.2 x 6.0 mm  @(2.0, 12.0)
  F2   6.0 x 4.5 mm  @(30.0, 26.0)
  F3   9.5 x 3.2 mm  @(40.0, 4.0)
  F4   3.0 x 1.2 mm  @(44.0, 8.0)
  ...
单层可用（仅 F.Cu）：F1, F3b(9.5x2.0)
仅 B.Cu 可用：R1 15.0 x 4.0 @(20,12)
```

于是"放一个 8×6 的模块"→ 模型只需比大小：F1 放得下，F2 差一点。**不需要任何空间推演。**

## A4. 通道（corridor）分析：回答"哪边走不过、为什么"

```
CORRIDORS
  ch_power_mcu  (power → mcu, 4 nets, 需 4×0.2mm+间距 ≈ 1.6mm)
    ch1 上方:  via r4, c26-c34  可用宽 3.1mm  ✅ 余量 1.5mm
    ch2 下方:  via r22,c26-c34  可用宽 1.2mm  ❌ 差 0.4mm
               原因: B1(U1 本体) 与 B3(GND 覆铜) 夹住；
               B3 可避让 → 可用宽可变 2.0mm，仍不足
    结论: 走 ch1；若 ch1 被 VCC 占用则建议移 C2 0.8mm 打开隘口
```

**"原因"字段是必须的**：告诉 AI 是被谁夹住的，以及那个人能不能动。

## A5. 元件布局表（精确、但不冗余）

```yaml
components:
  - ref: U1   block: power  at: [12.4, 8.2]  rot: 0    side: top
    body: 5.0x5.0  courtyard: 6.4x6.4  pins: 8  fixed: true
    nets: [VIN, GND, SW, FB]
  - ref: C3   block: mcu    at: [28.1,14.0]  rot: 90   side: top
    body: 1.6x0.8  courtyard: 2.2x1.4  pins: 2  fixed: false
    rel: {anchor: U2.pin1, dx: 2.4, dy: -1.0}     # 相对锚点，供模型推理
    nets: [VCC, GND]
```

`rel` 与绝对 `at` 同时给：模型对"距 U2 电源脚 2.4mm"的推理远强于对 `[28.1,14.0]` 的推理。

## A6. 采样粒度（必须显式声明）

永远标出这份 digest 的精度，否则模型会以为精确：

```
digest_version: 3   grid_pitch: 1.0mm   grid_origin: board_ll(0,0)
sampled_at: step7   precision: "grid 1mm; 小于 1mm 的间隙会被吞掉"
warnings: ["c33-r12 有 0.6mm 隘口被 1mm 栅格吞没, 见 blockers B7"]
```

**小于栅格的隘口必须单独列出来**，这是栅格化最容易造假失败的地方。

# B. 经验累积模块

## B0. 先分清两类"经验"——混在一起会互相污染

| 类型 | 例子 | 形态 | 处置 |
|---|---|---|---|
| **硬规则**（可机判） | "写 wire 后端点必须吸附引脚"""电源类 net 宽度 ≥1.0mm""0.65mm pitch 只能用 0.15/0.15" | 判定函数 | 变成**闸门断言**，apply 前自动跑，违反即 error |
| **软经验**（叙述性） | "这个封装的实际 courtyard 比 datasheet 大 0.5mm""本系列 LDO 输出电容不能小于 10µF，否则启动振荡" | 文本 + 触发条件 | 在对应 stage **注入上下文**，靠模型理解 |

**两条链：软经验由人/自省升级成硬规则。** 经验越多，硬闸门越多——这是"少犯同样的错"真正的机制，光靠塞提示词不会下降错误率。

## B1. 经验条目结构

```yaml
id: exp-0017
schema: 1
scope:
  eda: [kicad, easyeda]        # any / 具体
  stage: routing               # schematic | placement | routing | drc | export
  tools: [add_track, autoroute]
trigger: "net_class 未指定就走 autoroute"
claim: "默认 0.2mm 宽会让 VIN 类 DRC 挂"
action: "autoroute 前对 power 类 net 显式设 width ≥1.0mm"
evidence:
  runs: 5
  hits: 4                       # 该经验正确预测的次数
  violated: 1                   # 被违反且真出事的次数
  sources: ["2026-10-20 项目A#submission-xxxx", "exp-run-0031"]
confidence: 0.80                # 0~1，≥3 次独立命中才升档
status: active                  # candidate | active | retired
kind: hard                      # hard | soft
owner: local | butian           # 单写归属，见 B3
created_at / last_used_at
```

## B2. 闭环（对应补天的 recall → execute → feedback → dream）

```
① recall     进 stage 前按 (eda, stage, tools) 召回 top-k 经验
             附进 digest 的 `experiences:` 段（不是让模型自己去调）
② gate       hard 类：apply_plan 前确定性校验，违规 → severity
             soft 类：把 claim + action 注入当前 step 的上下文
③ outcome    每次 apply/validate/repair 后写 outcome 记录：
             { stage, plan_id, applied:[exp_ids], violated:[], new_violations, drc_delta }
④ feedback   经验命中且避免错误 → hits+1；被违反且出事 → violated+1 并降 confidence
⑤ candidate  同一 outcome 模式重复 ≥3 次且未收录 → 生成 candidate
⑥ promote    candidate 只有在人确认（或补天 dream 自省 + 独立验证）后才升 active
             hard 类还要求能被写成断言函数
```

**红线：candidate 不得自动升 active。** 经验库一旦被幻觉污染，后面每一步都在错的先验上推理，比没有经验更糟。

## B3. 与补天的对接（三种接法，选一种，不要都做）

| 接法 | 适用 | 做法 |
|---|---|---|
| **A. 直连** | 补天暴露 HTTP/本地 socket | 我们的 server 内部直接 recall/record，用户无感 |
| **B. 宿主编排** | 补天只暴露 MCP tool（最常见） | 我们返回 `{backend:"butian", action:"请调用 butian 经验召回(member=..., scope=...)"}`，由宿主/模型去调，结果回填到 `experience_apply()` |
| **C. 数据目录只读** | 补天本地落盘可读 | 只读同步经验库做 gate，写入仍走补天 |

> **硬约束：MCP server 之间不能互相调用**（协议上服务器是终端，不是客户端）。
> 所以"装了就切补天"在 B 场景下必须承认是**协作式**的，不能假装自己能接管；静默切换成"经验为空"就是最坏的结果。

## B4. 开关与单写原则

```yaml
experience:
  mode: auto            # auto | butian | local | off
  local: {dir: ./.pcbexp, max_entries: 2000}
  butian: {member: auto, recall_k: 8}
```

`auto` 的探测顺序（每次启动 + 每次 stage 切换各探一次，带缓存）：

```
1. 读配置 mode
2. mode=off → 关闭（tool 返回 {backend:"off"}，不报错）
3. mode=butian / auto：
     probe 补天（butian_status 或本地数据目录 or HTTP health）
     可达 → backend=butian，本地库降级为只读导出
     不可达（auto）→ backend=local，并在 digest 里显式标注
                     "experience_backend: local (butian unreachable)"
4. 任何情况都只有一个 active 写后端
```

**三条防呆**

1. **单写**：补天在场时本地库不写。两处同时写 → 两份经验互相矛盾 → AI 更糊涂（比没有更差）。
2. **显式降级**：见不到补天就明写 `local`，绝不静默当"没有经验"。
3. **可迁移**：`experience_export()` / `import()` 双向，保证用户换模式时经验不丢。

## B5. 注入位置（决定这套东西有没有用）

经验不是"给模型看一段话"，而是长在流程的固定节点上：

```
propose_plan  → digest.experiences[]         （soft：该注意什么）
apply_plan    → hard_gate(plan) → 拒绝/告警   （hard：不满足不让过）
autoroute     → 先强制 net class 检查         （hard）
validate      → 把 violation 与已知经验比对   （反馈，喂 outcome）
每次结束      → outcome 落盘 → candidate 检查
```

**判断这套模块有没有生效，只看一个指标：同一类 DRC/ERC 违规的复现率是否随轮次下降。** 不下降就是经验设计错了（太多太泛、没进闸门），而不是模型不行。

# D. 验收

1. **信息充分性**：把 digest 给模型，让它回答"8×6 的新模块放哪"，答案必须落在某个 FREE RECT 上且给出面积比较——做不到就补字段。
2. **不可通行可解释**：任意一条 corridor 的判定，必须能追到具体 blocker id + mutability。
3. **经验有效性**：跑 5 轮同类任务，某类违规的复现次数从 ≥3 降到 0；且 `experience_gate` 能拦住全部 hard 经验。
4. **不双写**：补天在场 → 本地库写入计数恒为 0（可断言）。
