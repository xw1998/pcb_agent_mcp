# 一帧的体积上限与「写不出去也不断线」（0.0.112）

## 这份文档回答什么

用户的原话是「建议改进mcp，现在还是断了」。断线在 MCP 这一侧只有四种长相：

1. 一条回复太大，宿主把它截断，这一轮就读不完整；
2. **一帧**（一行 JSON-RPC）超过读行那侧的上限，宿主报的是「连接断了」；
3. 进程自己退出（异常冒出 `serve()`），客户端只看到 EOF；
4. 一个请求永远不返回，宿主超时。

0.0.104 管住了 (1) 的一半（单条 `tools/call` 48 KiB），0.0.109 管住了
`tools/list`（25 KiB），0.0.108 管住了 (4)（可取消、可设超时）。
**(2) 和 (3) 在 0.0.112 之前完全没有闸门**，这份文档是补上它们时量到的东西。

## 实测：一帧可以有多大

前两道闸门都是「每条回复」，而一个批次是**一帧**。2026-11-04 在本机实测
（`_scratch/_m_line.py`，用 `serve()` 配 `BytesIO` 假 stdin/stdout，不走推理、只读输出）：

```
8 × tools/call calc_capabilities  ->  一行 279 633 B
```

八条回复每条都合法（各自 34 954 B，都在 48 KiB 以内），拼起来 273 KiB。
这不是「答得太大」的问题，这是「帧」的问题：读行那侧只要有一条上限，就得
把这一行判成坏帧。

上限不是猜的：本机 Python 3.12 的 `asyncio.StreamReader`（MCP 宿主最常见
的读法之一）`_DEFAULT_LIMIT = 65536`，超了直接抛。核过：

```
python -c "import asyncio.streams as s; print(s._DEFAULT_LIMIT)"  ->  65536
```

所以默认值取 **64 KiB**，并且**故意高于 48 KiB 的回复上限**：默认配置下
没有任何一条回复会被这道闸门碰到，它是协议的地板，不是对「答案能多大」的
第二种意见。

## 改了什么

### 1. `PCB_AGENT_MAX_LINE_KB`（默认 64，0 关闭）

`server._line_for_wire(payload, limit)` 在**变成字节之前**压预算：

- 单条回复超限 → 换成回执：保留 `id`，`reason_code=LINE_TOO_LARGE`、
  `bytes_full` / `cap_bytes`、原文头部 240 字符（不够就 80、再不够 0 字符），
  外加一句「这条是回执不是读数」；
- **批次按元素分预算**（`limit // len`），一条都不丢——丢掉其中一条是协议
  错误，客户端会拿到一个和请求不对应的数组；
- 装得下的回复 **逐字节不变**（不加键、不重排）。这条是「默认零变化」的
  可执行定义，自检里有一条专门比对 `_line_for_wire(resp, cap) == _dumps(resp)`。

### 2. `write()` 只捕 `OSError` → 捕一切

以前 `_dumps` / `encode` 抛任何非 `OSError` 的异常，异常会一路冒出 `serve()`，
进程无声退出、客户端看到 EOF、日志里**什么都没有**——和「客户端走了」长得
一模一样。现在：

- 记一行日志（说明这**不是**客户端离开）；
- 换成裸信封（`_emergency_envelope`）**重试一次**；
- 只有 stdout 真的关了、或第二次仍失败，才收线，并且明说是因为不愿写出一行
  坏帧去把客户端搞成不同步。

## 自检里加了哪四条（都带能失败的反向对照）

| # | 断言 | 它怎么失败 |
|---|---|---|
| 1 | 8 条合法回复的那一帧 ≤64 KiB，8 个 id 齐全，每个超限元素都带 `LINE_TOO_LARGE` 回执 | 删掉 `_line_for_wire` 就回到 279 633 B（实测） |
| 2 | `PCB_AGENT_MAX_LINE_KB=0` 时同一批次回到约 279 kB | 若设 0 不再恢复原行为，说明闸门写错了位置（改写而不是跳过） |
| 3 | 装得下的回复逐字节不变 | 若在 `_fit_one` 里顺手加了键或重排，这条就红 |
| 4 | 一个第一次 `write` 就抛 `ValueError` 的 stdout 之后，**下一个请求仍然被答**（ids 51、52 都在） | 改回只捕 `OSError`，第二个请求不会到达，这条红 |

实测输出（`_scratch/_m_line3.log`）：

```
capped line bytes: 7411 ids: [20,21,22,23,24,25,26,27] 0.02s
uncapped line bytes: 279643
untouched identical: True 380
[pcb-agent-mcp] could not write a reply (ValueError: boom); retrying with a bare envelope instead of ending the session
flaky ids: [51, 52] attempts 3
```

整轮自检：**354/354 passed（116.8 s）**。注意必须 `env -u PCB_AGENT_NGSPICE`
再跑：本机 shell 里有这个环境变量泄漏，它指向机器自装的 ngspice-47，会让
三条「打包引擎」检查变红——那是环境的错，不是代码的错（本轮先误判成
`find_ngspice` 的优先级 bug，改完才发现真因是环境变量，已回滚）。

## 本轮顺手核到、但**没有**改的

`calc/spice.py::find_ngspice` 的 docstring 原本写着「bundle 排在 PATH 与
安装目录扫描之间」，而代码里 bundle 其实排在 PATH **之后**。按
「不静默改变既有答案」的要求，只改了那段描述，没动排序：`PCB_AGENT_NGSPICE`
和 PATH 是「这台机器装了什么」的显式陈述，不该被一个随仓库走的二进制盖掉。

## 还没解决的

- 单条回复 48 KiB 仍是「一次读不完但也不会断」的量级；真正的解药是让工具
  默认分页、`saved_to` 变成常态而不是例外，这属于各工具自己的账。
- 自检汇总的计数不一致（`---- 353 checks` vs `354/354 passed`）仍然存在，
  0.0.112 没有碰它。
