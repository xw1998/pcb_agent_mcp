# 99 · 板子画对了，图是白的：整板平移与「出图落在页面外」

> 它回答的问题：DRC 已经 **118 → 0**、Gerber 也导出正常的一块板，为什么 `board_plot` 给的
> PDF/SVG 是**一张白纸**？
>
> 它推翻的前提：**「出图参数没配对」**——`kicad-cli pcb export pdf` 没有「居中」这个选项，
> 它把内容按**文件里的坐标原样**摆到页面上；板子画在负 Y，纸就在板子的下面。

---

## 99.0 两句话

1. 新增 op **`translate_board(dx, dy)`**：整板所有对象按同一增量平移（mm，**Y 向上**，
   与 `board_view` 报的是同一个坐标系），不点名的轴按 0 处理，`dx = dy = 0` 直接拒绝。
2. 这个 op 是**fail-closed** 的：板上出现一个它不认识的顶层对象种类，整笔拒绝
   （`UNSUPPORTED_ITEM`），而不是「把认识的搬走、不认识的留在原地」——后者会让一块板静默裂成两半。

---

## 99.1 触发它的三个读数

STM32F412RGT6 核心板（`_scratch/f412rg/stm32f412rg_core.kicad_pcb`，587 166 B）DRC 清零后出图：

| 读数 | 值 | 怎么量的 |
|---|---|---|
| `board.pdf` 内容 bbox | `Rect(1.4, −84.98, 149.8, −1.4)` | `pymupdf` 读页内所有绘图的包围盒 |
| `kicad-cli` 直出的 `direct.pdf` | `Rect(2.7, −83.2, 146.4, −2.3)` | 同上，绕开本仓库的导出包装 |
| 同参数导出**真实板** `StickHub.kicad_pcb` | `Rect(401.8, 226.8, 448.6, 338.5)` | 页面 841.9 × 595.3，**在页内** |

第三行是关键：同一段导出代码、同一个 `kicad-cli`，真实板落在页内，本板落在页外。
所以不是出图参数的问题。板子自身的文件 Y 在 **−30.48 … 0**，整板位于负 Y；PDF 页的原点在
左上、Y 向下为正，负 Y 就是**纸的上方**，被裁掉了。SVG 同理（板元素 y 为 −27.5 … 48.3）。

Gerber 不受影响：`stm32f412rg_core-Edge_Cuts.gbr` 里是 `X0Y0 … X53340000Y30480000`
（0–53.34 × 0–30.48 mm），钻孔/阻焊的导出器自己做了归一化。**也就是说，这块板拿去打样是全对的，
只有给人看的图是白的。**

三次绕过都失败，一并记下来，省得下次再试：
`pixmap(clip=…)`（clip 越界直接不渲染）、`set_mediabox(负 y)`（被裁回原页）、
cairosvg 换 `viewBox`（svg 里板元素仍是负坐标，换个视窗等于换个地方看空白）。

## 99.2 为什么是「平移整板」而不是「出图时加偏移」

给导出加一个页内偏移，等于让**出图**和**文件**说两套坐标：此后任何「图上的位置 ↔ 文件里的位置」
的换算都要带上那个隐藏偏移，而 DRC 报的 `items[].pos`、Gerber 的 X/Y、`board_view` 的焊盘坐标
全都是文件坐标。一个只影响渲染的偏移，是这堆坐标里唯一没有出处的那个。

平移整板则相反：**所有**读数一起动，相对几何一点不变——这也是它可验证的原因（见 99.4）。

---

## 99.3 它搬什么、不搬什么

三条规则，缺一条就会静默出错：

| 顶层对象 | 处理 |
|---|---|
| `segment` / `arc` / `via` / `zone` / `gr_*` / `dimension` / `target` / `image` / `group` | 搬（含 `zone` 的 `polygon` 与 `filled_polygon`，铺铜轮廓与已灌铜一起走） |
| `footprint` / `module` | **只搬它自己的 `(at …)`**：封装内部的焊盘、丝印、字段坐标是**封装自己的坐标系**，跟着父对象走，再搬一次就搬了两遍 |
| `version` / `generator` / `general` / `paper` / `layers` / `setup` / `title_block` / `net` / `net_class` / `property` / `embedded_*` / `lib_symbols` | 不搬 |

`setup` 是**整块跳过**的，理由写在代码里：它装着 `aux_axis_origin` / `grid_origin`，
那是**看图用的原点**，不是铜。搬铜的同时搬走一个绘图原点，是一笔没人要求的改动。

认得的位置写法只有六种：`at` / `start` / `end` / `mid` / `center` / `xy`，其余都是容器，继续往下走。

## 99.4 后置条件：位置的指纹

平移**没法用「绝对值等于多少」来验**——要验的正是「每个点都动了、且动的量一样」，而
「之前在哪」只存在于运行期。所以 `run` 把平移前后**所有位置**（遍历序，文件坐标）各取一个
sha256 指纹写进 record，`verify` 在**写完的文件上重算**并逐项对照：

| 检查 | 抓的是哪种错 |
|---|---|
| 位置个数相同 | 少搬/多搬一个对象（比如某个容器被漏掉） |
| `digest_after` 相同 | 有点没动、或动的量不一样——这是主判据 |
| record 里的 `dx/dy` 与请求一致 | 参数在 record 与 verify 之间被换过 |
| `digest_before ≠ digest_after` | 跑了一个什么都没做的「平移」 |

**写死的局限**（`verify_limit` 字段里也写着）：指纹是位置的**多重集**，它证明「这些位置整体
动了这么多」，不证明「每个位置仍属于原来那个对象」——一次自相矛盾的置换在数学上可能撞上同一个
指纹。这是这一版承认的边界，不是可以忽略的细节。

反向对照（`tests/test_ops_edit.py::TranslateBoard`）：写成功之后，把一个角点改回原处，
再拿同一个 record 跑 `verify_all`，必须 `all_verified = False`，且理由里必须有
「not the ones the run computed」。**如果这条对照不红，主判据就是空的。**

## 99.5 六条测试

1. 板上每个非封装对象都动了同一个增量（边界线、线段、过孔、两个 zone 的多边形首点、封装 `at`），
   且 `items_total` = 10；
2. **封装内部坐标不动**（焊盘仍在 (−0.95, 0) / (0.95, 0)，参考字段仍在 (0, −2)）；
3. 带 30° 旋转的封装：位置动、**角度留着**；
4. `dx = dy = 0` → `ARG_INVALID`；
5. 板上出现一个不认识的顶层种类（构造 `(table (column_count 2) (at 5 5))`）→ `UNSUPPORTED_ITEM`，
   **且文件一个字节都没变**；
6. 反向对照（99.4）。

Y 的符号在这六条里各验了一次：`dy` 是**向上**的，而文件里的 Y 向下，所以 `dy = 25`
让文件 Y 从 10 变成 −15。这条符号弄反了，图不会白，但板子会镜像——最贵的一类错。

---

## 99.6 三条教训

1. **「板子对」和「图对」是两件事**：Gerber 归一化过、DRC 用的是文件坐标、出图用的是页面坐标，
   三者对原点/朝向的约定不同。任何一处出问题，都只会以「某个下游看起来是空白」的形式暴露。
2. **给渲染打偏移是最省事、也最贵的修法**：省了一次数据改动，代价是此后每条坐标都要问「这是文件坐标
   还是页面坐标」。能改数据就不要改坐标系。
3. **能整体搬，才敢整体搬**：先分清「谁是板坐标、谁是封装局部坐标」，再决定搬什么。
   搬两遍和漏搬，在文件里都长得像「有点不对」，而 DRC 只会在下一轮用一堆 `clearance` 告诉你。

## 99.7 让工具自己说这件事（0.0.102）

99 记的是**人**怎么发现并修好一次白图：量 DRC、量坐标、把整板搬走。但换一块别人给的板子，
没有人替他做这三步——`board_export_graphics` 只回一个 `status: ok` 和一串文件路径，
而「文件是真的、纸是白的」这件事，恰恰长得最像成功。

0.0.102 起，`pdf / svg / ps / dxf` 的每次出图都多带一个 `placement` 字段，由
`fab.board_extent(path)` 算出。它不画图、不改文件，只回答两件事：**这块板在文件坐标里占多大、
纸装不装得下**。同一块 F412 板，平移前后各量一次：

| 板 | bbox（文件坐标，mm） | 位置数 | `negative_axes` | `fits_paper` | `warnings` |
|---|---|---|---|---|---|
| `stm32f412rg_core.kicad_pcb`（平移后） | 20.00..73.34 × 20.00..50.48 | 15 315 | — | `true` | 0 条 |
| `backup_pre_translate.kicad_pcb`（平移前） | 0.00..53.34 × −30.48..0.00 | 15 315 | `["y"]` | `false` | 1 条 |

两块板是同一个设计的同一批对象（位置数 15 315 一致），第二个盒子整体平移了
`dx = +20.00, dy = +50.48`——这就是 99.4 那条「位移后位置指纹要变、对象数不许变」的后置条件，
现在变成了出图前就能读到的两个数。

警告里不再只说「用 translate_board」，而是把参数算出来：

```json
"advice": {"op": "translate_board", "dx": 0.0, "dy": -30.48,
           "note": "the edit API is y-up, the file is y-down: this dy moves the
                    design just far enough to clear the origin"}
```

**符号是这里唯一的坑，也是它值得单独一个字段的原因**：编辑层是 Y 向上、文件是 Y 向下，
所以抬高一块 `y_min = −30.48` 的板，`dy` 要填 **−30.48**（等于 `y_min` 本身），
而不是它的相反数。填反了不会白图，板子会朝纸外多走一个板高——99.5 第 6 条把这条符号
在 `translate_board` 里验过一次，这里再验一次，且是端到端的：

`test_the_advice_actually_clears_the_warning` 把 `dx/dy` **从警告里读出来**（不是写在测试里），
`translate_board` 之后重出一张 PDF，要求 `warnings` 消失、`fits_paper` 变真、
`bbox` 的 `y_min` 恰好落在 0.00。建议只要还只是文案，这条测试就会红。

「量不出来」一律不写成「装得下」：

| 情形 | 返回 |
|---|---|
| 文件读不了 / 解析不了 / 一个位置都没有 | `None`（`placement` 整个不出现） |
| `(paper "LedgerX")` 这类不认识的纸名 | 不出现 `paper`，也不出现 `fits_paper`——**不判** |
| `(paper "User")` 但没给尺寸 | 同上，不判 |
| `(paper "User" 100 80)` 自带尺寸 | 按 100×80 判，超了照报 |
| 板在负坐标 | `negative_axes` + 1 条警告 + `advice` |
| 板比纸大 | 1 条「clipped, not scaled」，**不与负坐标混成一条** |

最后一行是这一轮改过一次的地方：负 Y 的板最初会同时收到「落在负坐标」和「比纸大」两条警告
（按坐标算它确实越界了），一因两果。现在两种原因分开判——板在纸内但坐在负半轴时只报负坐标，
真的比纸大时才报尺寸。

`status` 永远是 `ok`：文件确实生成了，把「纸会是白的」降级成错误，等于否认一个真实产物。
警告是加法的，只在触发时出现；不触发时，返回体与 0.0.101 逐字节相同。

八条测试各自能失败的方式（`tests/test_graphics_placement.py`）：盒子等于刀框而不是别的东西
（4 条边 8 个点 + 封装原点 1 + 走线 2 + 过孔 1 = 12 个位置，过孔漏了就会「装得下却裁掉」）、
负 Y 被点名且 Y 不被偷偷翻转、超宽只报尺寸、自定义纸按自带尺寸判、纸名不认识时不判、
读不了文件的返回 `None`、白图仍是 `ok` 且带警告、按警告执行后警告消失。

三条诚实披露：

1. **盒子是「位置」的盒子，不是铜皮的盒子**：它和 `translate_board` 走的是同一个遍历
   （`_board_points`），封装只取自己的原点，焊盘/丝印在封装局部坐标里、跟着走。
   所以一个封装本体比它原点更靠外时，盒子会比真实铜皮小几毫米——它回答的是
   「整板搬到哪」，不是「铜皮的外接矩形」。
2. **纸张只按名字查表，并统一按横向算**（`max` 当宽）：`(page_settings)` 里的朝向与边距不读。
   一张 `A4` 竖排的板，若宽度在 210..297 之间，这里会判「装得下」而实际出图不会。
3. **它不替人改文件**：`board_extent` 是只读的，`advice` 只是一个建议块。
   什么时候搬、搬多少，仍然由调用方决定——这也是 99.2 那条「不要给渲染打偏移」的延续。
