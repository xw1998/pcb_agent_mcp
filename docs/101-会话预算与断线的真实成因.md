# 101 · 会话预算，以及「MCP 又断了」的真实成因

2026-11-04，用户第二次报「建议改进 mcp，现在还是断了」。这次先去宿主的日志里
找现场，不再猜。

## 1. 现场：断的不是管道，是对话的上下文

宿主 app-server 日志（`%APPDATA%\WPS 灵犀\logs\app-server\app-server_2026-11-04.log`）：

```
16:22:34  [context_compactor] compact success: c_compact, msgs=144->3,
          original_tokens=133868, compacted_tokens=61474, ratio=45.9%
16:29:28  recommendation decision ... answer_runes=111
16:30:35  session started
```

`answer_runes=111` 是一条 почти空的回复——用户看到的「断了」就是它：上一轮
131 万字符的上下文被强行压缩，紧接着这一轮什么都说不出来，然后会话重启。

更早的几次（同一天、同一会话）：

```
13:15:47  run terminal outcome ... err="agent run: code:OpenAIError
          message:{\"error\":{\"code\":\"UPSTREAM_TIMEOUT\",...}}"
14:12 / 14:19 / 15:18 / 15:25  err="agent run: empty choices"（5 次退避重试后放弃）
```

`empty choices` 与 `UPSTREAM_TIMEOUT` 都是**上游模型**给的，不是 stdio 管道。

## 2. 所以这一次的「断」不是 MCP 服务造成的

同一天这个会话里，所有工具都是 `bash_exec`（宿主自己的 shell），**一次
pcb_agent_mcp 的 `tools/call` 都没有发生过**。也就是说 0.0.112 修的那条路径
（写不出去的自定义异常 / 279 KB 单帧）这一轮根本没被走到。

诚实结论：**「断了」的直接成因是上下文被撑爆 + 上游模型返回空**，
`pcb_agent_mcp` 不是这一次的凶手。

## 3. 但这个 MCP 确实还在制造那个「撑爆」

一条 48 KiB 的回复约 12 000 token（没算进请求里的 system / skill / 历史）。
十次如实的 `board_view` / `board_drc` / `lceda_pro_run`，对话就花光了——
而每一次都在自己的闸门之内，任何一层都报绿。

所以第三次加固落在**会话**这一层：

| 闸门 | 版本 | 守的是 |
|---|---|---|
| `PCB_AGENT_MAX_RESULT_KB` = 48 | 0.0.104 | 一条 `tools/call` 的结果 |
| `PCB_AGENT_MAX_TOOLS_KB` = 25 | 0.0.110 | 一页 `tools/list` |
| `PCB_AGENT_MAX_LINE_KB` = 64 | 0.0.112 | 一帧 JSON-RPC（批次是**一帧**） |
| `PCB_AGENT_SESSION_BUDGET_KB` = 256 | **0.0.113** | **一整场对话** |

## 4. 语义（写死，别读错）

- 记账的是**真正进对话的字节**：`cap_result` 的每一条返回路径都调
  `note_reply_bytes(len(返回文本))`。工具内部算了多少字节不算数。
- 预算**未到时回包逐字节不变**。这一点有反向对照：同一条 29 KB 回包在默认
  预算下与 `result_to_text` 完全相同，`session_spent_bytes()` 恰好等于它的字节数。
- 预算**越过后**，后续回包按 `PCB_AGENT_SESSION_TAIL_KB`（6 KiB）收尾：
  - `reason_code = "SESSION_BUDGET"`（不是 `RESULT_TRUNCATED`：这条回答本来不大）
  - `session_bytes` / `session_budget_bytes` / `why_this_is_short` 三个字段说清原因
  - 全文照旧落 `saved_to`，模型可以读文件
- `PCB_AGENT_SESSION_BUDGET_KB=0` 完全关闭（体积与行为回到 0.0.112）。
- `serve()` 开头 `reset_session_budget()`：一个进程就是一场对话。

## 5. 验收

```
env -u PCB_AGENT_NGSPICE PYTHONPATH=src python run_server.py --selftest
→ 357/357 passed in 108.3s   (_scratch/_st113.log)
```

新增四条：逐字节不变 / 越界切到 6 KiB 且带 `saved_to` / 关掉后不切 /
「所以上面那条测的是闸门而不是自己变小的回包」。

## 6. 没解决的部分（不许当成已解决）

1. **上游模型 `empty choices` / `UPSTREAM_TIMEOUT` 不在本仓库能力范围内**：
   客户端重试 5 次仍空，服务端能做的只有把上下文压小、把回复变小。
2. **压缩本身会丢细节**：`msgs=144->3`、`ratio=45.9%` 之后，最早那批实测数字
   （saved_to 路径、某次 DRC 的原始计数）只能靠文件与记忆找回。
3. **预算值是测出来的还是拍的？** 256 KiB ≈ 65 000 token，是照着那次
   `original_tokens=133868` 压缩线压到一半取的**保守值**，不是从逆向出来的
   宿主阈值。它偏紧；真跑长任务时若觉得切得太早，把它调大即可，行为一致。
4. 会话内的 `note_reply_bytes` 只统计 `cap_result` 走到的路径；
   `tools/list` 与错误信封不受它约束（各有自己的闸门）。
