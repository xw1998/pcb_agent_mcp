# 103 — 一次回复能有多大（自查：为什么这个 MCP 又把对话撑死了）

> 起因（用户原话）：「自查mcp的问题，你现在又导致对话故障了」。
> 本文件只回答一件事：**这个服务自己产出的单条回复，凭什么认为对话能装得下。**
> 结论先说：在 0.0.104 之前，这个服务里所有体积上限都是**传输界**（管道能搬多少），
> 没有一条是**对话界**（一次回复读进上下文还剩不剩地方思考）。0.0.104 把闸门挪到
> 对话界：默认 48 KiB，超了截断 + 落盘，并且「截断」要真的变短。

---

## 103.0 现场：这次的崩不是客户端的问题

0.0.103 之前，我在脚本里这样取数：

```python
from pcb_agent_mcp import tools as T
print(T.call_tool("lceda_pro_run", {"code": "return await getAll()"}))
```

`tools.call_tool()` 是仓库内的**唯一调用入口**，`server.py` 的 JSON-RPC 分支也是转调它。
区别只有一个：**`call_tool` 是进程内直接返回 Python 对象，不经过 server 层的体积闸门。**
于是闸门再严也拦不住这条路，而脚本顺手 `print` 出来的东西是：

| 调用 | 实测体积 |
|---|---|
| `lceda_pro_run` → `return await getAll()`（PCB 器件/焊盘全量） | 几十万字节（随板上对象数线性长） |
| `board_view kind=pads`（194 个焊盘，改动前每页 64 KiB 能一次装完） | 109 190 B（落盘 `_scratch/f412_pads.json`） |
| `pcb_PrimitivePad.getAll()`（194 条 × ~500 B） | 约 97–109 KB |
| `calc_capabilities` | 68 089 B（其中 `not_implemented_yet` 一项 38 295 B） |
| `lceda_pro_api`（不带 `class_name`） | 378 条类型，一次 11 281 B（`_scratch/_lc_api3.log`）且无分页 |
| `lib_Device.search` 8 个关键词 × 5 条 | 数十 KB（每条带 `otherProperty` 全集） |

一次 109 KB 的 JSON 大约是 3 万 token。对话不是被「内容错」搞死的，是被**单条回复的体积**搞死的。

## 103.1 四级「上限」逐个量：全是传输界

改之前的仓库里能找到四个数字，看上去像是有保护，实际全都比对话容量大一到两个数量级：

| 位置 | 常量 | 值 | 它真正在保护什么 |
|---|---|---|---|
| `tools.py` `board_view` | `_VIEW_MAX_BYTES` | 65 536 B（64 KiB） | 一页视图不要太大，但 64 KiB ≈ 2 万 token，本身就是一次会话事故 |
| `tools.py` 全局闸门 | `PCB_AGENT_MAX_RESULT_KB` 默认 | 1024 KB | 管道别噎住；1 MiB 的回复没有任何对话能读 |
| `lceda_live.py` | `MAX_REQUEST_BYTES` / `MAX_REPLY_BYTES` | 4 MiB / 16 MiB | 本地命令空间的帧边界 |
| `lceda_api.py` | `MAX_FRAME` | 16 MiB | 同上，桥的帧长 |
| `ledger.py` | `MAX_BYTES` | 4 MiB | 台账轮转，不是回复 |

**这不是「数字调小了」的问题，是「这几个数字回答的根本不是同一个问题」。**
管道关心的是「搬得动吗」，对话关心的是「读进来以后还有没有地方推理」。前者 16 MiB 都算正常，
后者 30 KB 就已经很重了。把传输界当对话界用，就会出现在 64 KiB 的页上跑得好好的、
一到对话里就把上下文挤爆的怪现象。

## 103.2 定这个默认值：拿实测的两个边界夹出来

不猜，量两头：

- **最大的「诚实答案」**：`board_ops`（写能力目录）**33 340 B**，41 条 KiCad 操作 + 6 条 epro 操作。
  这是一次正常问答，用户问「你能写什么」，答案不该被砍。
- **最小的「一次倾泻」**：`calc_capabilities` **68 089 B**；再往上是 `board_view` pads 109 190 B、
  `lceda_pro_run` 的整对象几百 KB。

所以默认取 **48 KiB（49 152 B）**：在 33 340 B 之上（诚实答案原样通过），在 68 089 B 之下
（第一次真正的倾泻就开始被截）。同时把 `board_view` 的单页上限从 64 KiB 降到 **16 KiB**，
因为分页是它自己的事，`limit` / `offset` / `max_bytes` 都在，没必要一页给 64 KiB。

## 103.3 为什么不继续「整包丢弃」

0.0.96–0.0.103 的做法是：超过上限就回

```json
{"status": "error", "reason_code": "RESULT_TOO_LARGE", "bytes": 109190, "hint": "..."}
```

问题不是「错」，是**代价全在调用方**：查询已经跑过了，CPU 和 IO 都花了，拿回来的只有一句「太大了」。
对话那边也没得到任何可用信息，只能重跑一个更窄的查询——而窄到什么程度，仍然靠猜。

0.0.104 改成：**保留头部 + 完整件落盘 + 说清怎么收窄**。

实测的一次（`calc_capabilities`，48 KiB 上限、完整件 68 089 B）：

```json
{
  "status": "ok",
  "truncated": true,
  "reason_code": "RESULT_TRUNCATED",
  "bytes_full": 68089,
  "cap_bytes": 49152,
  "truncated_fields": {
    "layers.electrothermal (string)": {"kept": 2000, "total": 2348},
    "not_implemented_yet[]": {"kept": 4, "total": 23, "budget_bytes": 8192},
    "not_implemented_yet[] (string)": {"kept": 2000, "total": 6129}
  },
  "saved_to": "C:\\Users\\...\\Temp\\pcb_agent_mcp_results\\20261103-133340-calc_capabilities-68089.json",
  "where_the_rest_is": "the complete reply is the JSON file at `saved_to` (68089 bytes); ...",
  "how_to_shrink": "ask for less: board_view kind=/limit=/offset=/max_bytes=, ...",
  "where_to_read": "this IS the tool's answer, cut to fit the conversation; the uncut JSON is at `saved_to`"
}
```

截断后这一条是 34 162 B（上限 49 152 B），`available` 的 186 个名字一个不少，被砍的只有
`not_implemented_yet` 的长文本。

三条硬性质，缺一条这个改动就是自欺：

1. **没超上限的回复逐字节不变**（不加键、不重排）——否则「截断」会变成「静默改写别人的答案」。
2. **超了就必须真的变短**：返回的文本长度 ≤ 上限。
3. **切得再狠也不能把「一串名字」切成 8 条**，因为那不是在压缩，是在给出错误的答案。

## 103.4 三个当场翻车，和各自的修法

第一版（保留每个列表前 8 项、每个长串前 2000 字符）一跑自检就红了三条，值得逐条记下来，
因为三条都不是「实现 bug」，是**设计想错了**：

### 翻车一：把 186 个工具名砍成 8 个

`calc_capabilities` 的 `available` 是 186 个工具名（3 682 B）。按「前 8 项」截，`board_summary`
（第 22 个）就没了，自检 `capabilities lists the board tools` 直接 FAIL。

> 一串名字是**一个答案**，不是一张表的行。砍成 8 条等于回答「一共有 8 个工具」——错答案。

修法：列表按**字节预算**装，装到装不下为止（`_CAP_LIST_BYTES = 8192`），不再按条数。

### 翻车二：「截断」之后仍然 34 KiB，超过它自己声称的上限

同一版里，`calc_capabilities`（68 089 B）截完还是 34 931 B，而上限是 24 576 B。
一个叫「截断」的函数产出比它自己声称的上限还大的东西，这是最坏的一种错——**读数自相矛盾**。

修法：`_CAP_SCHEDULE` 逐档收紧 `((8192, 2000), (2048, 800), (512, 300), (128, 120), (32, 60))`，
每档量一次，落进上限就返回；五档都不行就退化成「只有形状和计数」（`_spine_reply`）；
连这也装不下（上限被设成 1 KB 时实测 1 918 B > 1 024 B）就退化成一张回执（`_minimal_reply`）。
实测：

| 上限 | 返回体积 | 形态 |
|---|---|---|
| 48 KiB（默认） | 34 162 B | 截断，`available` 186 个名字全在 |
| 2 KiB | 1 918 B | 只有形状与计数 |
| 1 KiB | 853 B | 回执（`saved_to` + `bytes_full`） |

### 翻车三：把 41 条写操作砍成 8 条

`board_ops` 33 340 B、41 条操作——比 24 KiB 的旧默认大一点点，于是被截成 8 条，
自检 `write catalogue covers both formats` 报 `kicad=8 epro=6`。

> 这条最值钱：它说明**「上限」不是越低越好**。太低的上限会让正常问答变成残废答案。
> 上限要按「实测的最大诚实答案」定，不是按「我觉得对话该多大」定。

修法：默认值从 24 KiB 抬到 48 KiB（见 103.2），并在自检里把默认值本身变成一条检查
（`the conversation cap defaults to 48 KiB`），附上 33 340 B 与 68 089 B 这两个实测锚点。

## 103.5 第四条翻车（不是代码，是自检的分工）

修完上面三条，`magnetics_data` 的三条粉芯表检查仍然红：期望 500 行，读到 27 行
（另一次跑读到 64 行）。原因不在数据：**默认闸门开着，那三条检查拿到的是被截断的回复。**

这里要写死一条分工，否则以后还会犯：

> 自检里「量数据」的检查，必须在闸门关闭下跑；「量闸门」的检查，自己显式设上限。
> 两者混在一条路径上，红色既可能是数据错，也可能是闸门在按设计工作——两种红分不开，
> 就等于没有判据。

落法：`selftest()` 开头把 `PCB_AGENT_MAX_RESULT_KB` 置 `0`（正文检查看完整答案），
结尾恢复，并新增一条**默认值检查**（在真正的空环境下量 `max_result_chars() == 48 * 1024`）。
闸门本身由四条检查负责，其中一条是反向对照（把上限设成 0，同一份 payload 不许被切），
保证「前面几条不是在量一个恰好很小的 payload」。

```
unittest tests.test_tools tests.test_server_protocol tests.test_tools_profile
  → 46 tests, OK
python -m run_server --selftest → 336/336 passed, rc=0
```

四条闸门检查（都在 `server.py` 的 selftest 末尾，逐条可失败）：

| 默认值是 48 KiB | `max_result_chars() == 49152`（空环境） | 用 33 340 B / 68 089 B 两个实测锚点说明为什么 |

## 103.7 还没做的、以及怎么用才不出事

- **`tools.call_tool()` 进程内调用仍然不受闸门保护。** 这是本轮崩溃的直接路径，但它不能靠闸门修：
  闸门活在 JSON-RPC 分支上，进程内调用根本不经过。正确用法是「脚本里只 `print` 计数与前 N 项，
  完整对象先落盘再 `head` 读」。这条没有任何机制能替人记住，只能写在这里。
- **`board_components` / `board_nets` 已分页**（默认 100 条一页，回 `total` / `truncated` / `next_offset`），
  `board_view` 用 `kind=` + `limit` / `offset` / `max_bytes` 分页（`max_bytes` 默认 16 KiB，
  `kind=all` 只回每类计数）。**真要整表，请用落盘文件，不要指望一次回复。**
- 想临时放宽：`PCB_AGENT_MAX_RESULT_KB=<n>`；设 `0` 关闭上限。放宽等于「我知道这一条回复会占掉多少上下文」，
  这不是一个可以随手设的开关。
- 落盘目录：`%TEMP%\pcb_agent_mcp_results\`，文件名 `<时间戳>-<工具名>-<字节数>.json`。
  这些文件不会自动清理，也不该由服务去删（用户的证据）。

## 103.8 88 MB 实板复核：同一块板，改前与改后

拿仓库根目录那块 `jetson-agx-thor-baseboard.kicad_pcb`（**88 747 390 B**，
1125 个封装 / 4862 个焊盘 / 22151 段走线 / 3235 个过孔 / 125 个 zone / 1388 个网络）复测。
量法只有一条：`call_tool` 拿到对象 → `result_to_text` 数字节 → `cap_result` 再数字节；
脚本 `_scratch/measure_jetson.py`，读数 `_scratch/_jetson_measure.log`。

| 调用 | 改前（一次全量） | 改后（实测） | 改后形态 |
|---|---|---|---|
| `board_view kind=all` | **95.6 MB** | **765 B** | 13 类计数（`nets 1388 / footprints 1125 / pads 4862 / tracks 22151 / vias 3235 / zones 125 …`） |
| `board_view kind=footprints` | 12.8 MB（200 条/页） | **15 436 B** | 一页 53 个封装，`total 1125`，`next_offset 53` |
| `board_components` | 371 KB（1125 个） | **28 489 B** | 100 条/页 |
| `board_nets` | 139 KB（1387 个） | **9 509 B** | 100 条/页 |

改后的四个数都在 48 KiB 闸门之下，而且**没有一个是被 `cap_result` 砍出来的**
（`cap_result` 对它们原样放行，`truncated` 是分页自己标的）：分页把「体积」这件事在
产出端就解决了，闸门只是兜底。

> 关于 `kind=footprints` 一行：0.0.103 的单页上限是 64 KiB，一页 200 个封装约 30–56 KB；
> 0.0.104 把单页降到 16 KiB 后，一页是 53 个封装、**15 436 B**。也就是说「修复后」这一列
> 在那一行上还落后一档——不是两种读法打架，是两个不同的单页上限。

### 一条同样要写下来的读法

分页只保证**一页**小，不保证**一轮对话**小：

- 想枚举完 1125 个封装 ⇒ `1125 / 53 ≈ 22` 页 × 15.4 KB ≈ **340 KB**，照样能压垮上下文；
- 想枚举完 22151 段走线或在 4862 个焊盘上做逐条判断 ⇒ 更是几十 MB 量级。

**所以「能翻页」不等于「应该翻完」。** 需要整表时走落盘文件（`saved_to`）或交给
计算层（`board_cross_check` / DRC / 统计）在文件上算完再回读数，不要在一轮对话里逐页搬运。

### 时间也是读数

同一块板上 `board_view kind=all` 花了 **78.2 s**（保真树要把 88 MB 全部解析一次），
`board_view kind=footprints` 7.5 s，`board_components` 47.0 s，`board_nets` 0.4 s。
这些是「一块 88 MB 板的真实代价」，不是超时故障；`DRC_TIMEOUT_S = 900` 的默认值就是照这个量级定的。
