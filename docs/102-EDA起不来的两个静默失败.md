# 102 · 立创 EDA 起不来的两个静默失败：`rc 0` 不是成功，继承的环境变量也是行为的一部分

## 102.0 两句话

`D:\LCEDApro\lceda-pro\lceda-pro.exe` 双击能开、从这个会话里启动却「1.25 秒后 `rc 0` 退出、
不建窗口、不建命令管道、日志一个字不写」——原因不是没装好，是**这个服务自己**的父进程是 Electron，
把 `ELECTRON_RUN_AS_NODE=1` 传了下去，于是被启动的 Electron 变成了一台裸 node：无参数就开 REPL，
stdin 是 EOF 就退 0。第二个静默失败在另一层：调用返回时整棵进程树被回收，就算前一条修好了，
窗口也会跟着一起消失。

## 102.1 四个读数，先钉住现象

| 读数 | 值 | 它排除了什么 |
|---|---|---|
| 退出码与耗时 | `rc=0`，1.25 s | 「崩溃」——崩了不会 0 |
| stdout / stderr | 都是 0 字节 | 「有报错被吞了」——根本没写 |
| 应用日志 `debug.log` | 停在 10-29，今天零新增 | 「app 起来了但初始化失败」 |
| 命名管道 `\\.\pipe\JLCEDAPro*` | 60 次轮询（15 s）一个都没出现过 | 「管道名变了 / 起得慢」 |
| 进程 | 启动 1.25 s 后 `lceda-pro` 计数 0 | 「在后台活着只是没窗口」 |
| exe 体积 | 222 977 648 B | 不是 node.exe（92 MB），是 Electron |

`unins000.exe` 在、`resources\app\app.js` 3.2 MB 在、`package.json` 里 `main: ./app.js` 在——
安装是完整的。完整安装 + 立刻退 0 + 不写日志，这三件事同时成立时，第一嫌疑不是安装，
是**它没按 app 的方式被启动**。

## 102.2 取证：这个 exe 究竟是哪种运行时

```text
$ ./lceda-pro.exe --version
v24.14.1
$ ./lceda-pro.exe ping
Error: Cannot find module 'D:\LCEDApro\lceda-pro\ping'
```

第二条是决定性的：它把 `ping` 当成**脚本路径**去 `require`——这是 node 的语义，不是应用的语义。
应用自己的命令空间（`activate / open / stop / ping`）根本没有被加载。

再看环境：

```text
$ env | grep -i electron
ELECTRON_RUN_AS_NODE=1
```

这个变量在 Electron 里的语义正是「别当 Electron，当 node 用」。它是**继承来的**：
本服务由 Electron 宿主启动，宿主设了它，子进程全带着。于是：

- 带参数 → Electron 按 node 处理参数（所以 `--version` 打出 node 的版本、`ping` 被当脚本）；
- 不带参数 → node 进 REPL，stdin 是 `DEVNULL`/EOF → **立即正常退出，`rc 0`**。

所以那个「1.25 秒、0 字节、0 管道」的形状不是故障，是**一台 node 干完了它被要求干的事**。
把变量摘掉再启动：

```text
pipe at 1.0s: ['JLCEDAPro0c65189e']
```

管道 1 秒就出现，`lceda_pro_status` 当场 `ok`，`bridgeVersion 4.1.60.198f38ab`。

## 102.3 为什么这条错了很久都没被抓住

旧记录写的是「从继承 console 的 shell 启动会 0.5 s 退出，用 explorer.exe 双击才能活」——
那是一条**真实的观测**，但归因错了。explorer.exe 那条路之所以能活，是因为
explorer 自己的环境里没有 `ELECTRON_RUN_AS_NODE`，它把这份「脏环境」洗掉了。
现象被记录成「启动方式有讲究」，真因是「环境变量会传染」。

这就是这一批最贵的一课：**一条测量可以是真的，而它的解释可以是错的**，
而且这种错会以「hint 文案」的形式固化进工具里，下一次照着 hint 做还是失败。

## 102.4 第二个静默失败：进程树在调用返回时被回收

环境修好之后还有一层。同一个 exe，用四种方式起，结果不同：

| 启动方式 | 1 s 时 | 命令结束后 |
|---|---|---|
| `subprocess.Popen`（继承当前 job） | 进程在、管道出现 | **被一起回收** |
| `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP` | 起得来 | 仍然被回收 |
| `Start-Process`（PowerShell） | 起得来（6 个进程） | 30 s 内消失 |
| 后台保活一个 launcher，让它一直挂着 | 进程在、管道在 | 只要 launcher 活着就一直在 |

`CREATE_BREAKAWAY_FROM_JOB` 在本会话里直接 `WinError 5 拒绝访问`（job 不允许 breakaway），
所以「脱离 job」这条路是被系统挡住的，不是写错了。结论不是「要怎么再试一次」，
而是：**「启动成功」与「启动之后还在」是两件事**，前者只证明 `CreateProcess` 返回了。

## 102.5 修法与它的判据

`desktop.launch()` 现在把子进程环境显式构造出来：

```python
_DROP_FROM_CHILD_ENV = ("ELECTRON_RUN_AS_NODE",)

def _child_env():
    """(env, dropped) - the environment an EDA child should get, made explicit."""
    env = dict(os.environ)
    dropped = [k for k in _DROP_FROM_CHILD_ENV if env.pop(k, None) is not None]
    return env, dropped
```

`launch()` 返回体里多一个 `env_cleared: ["ELECTRON_RUN_AS_NODE"]`——**被摘掉的键要报出来**，
否则「我替你把环境改了」这件事和「什么都没做」在返回值上长得一样。

判据不是「代码里有这一行」，而是**子进程自己怎么看**：`tests/test_desktop.py` 里
`test_launch_does_not_hand_an_electron_child_its_own_node_mode` 先把父进程的
`ELECTRON_RUN_AS_NODE` 设成 `1`，再启动一个只会打印自己环境的小脚本，要求它写下 `absent`。
写成 `present` 就红——包括「忘了传 `env=`」这种最容易发生的退步。

自检里同样加了一条（`--selftest` 331 → **332**）：把父环境设成 `1`，要求
`_child_env()` 的 `dropped == ["ELECTRON_RUN_AS_NODE"]` 且子环境里不含它。

同时把 `APP_NOT_RUNNING` 的 hint 重写了。旧 hint 把现象当原因（「从 shell 启动会 0.5 s 退出」），
新 hint 给两个**静默**的真因和各自的解法：摘掉变量（走 `app_launch`，它替你摘）
＋启动后要脱离调用方的进程树（`app_launch` 是 `DETACHED_PROCESS`）。

## 102.6 三条教训

1. **`rc 0` 不是成功**：一个进程正常退出，可能代表它做了**另一件事**。判断「起来了」要看
   它的产物（窗口、管道、日志、端口），而不是看退出码。
2. **继承来的环境变量是行为的一部分**：同一个 exe 在不同父进程下是不同程序。
   凡是「替我启动」的封装，都应该显式构造环境并**报出改了什么**，不要默默继承。
3. **工具自己写的 hint 也可能是一条错误归因**：hint 最容易被当成事实照抄，
   所以它必须写「测到了什么」，而不是「所以我猜是这样」。
