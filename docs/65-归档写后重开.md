# 归档写后重开：把「应用接受我们写的 `.epro`」从"不宣称"变成一次实测

日期：2026-11-01　仪器：LCEDA Pro **V4.1.60**（bridge `4.1.60.198f38ab`）

这篇回答一个此前每次 `board_apply` 都会自己声明"**没有**验证过"的问题：
**应用到底认不认我们写出来的 `.epro`？**

答案是：认，且只读到我们改动的那个值。但这句话有一个必须写清的口径范围（见 §5），
以及一个必须存在的方法论前提：**能下这个判的只有几何回读，不是导入返回值**（见 §4）。

---

## 1 要判什么，以及为什么 `open` 不能当判据

`lceda_live` 的 bridge 有一个 `open(path)` op。它**打不开 `.epro`**，实测：

| 调用 | 返回 | 随后 `getCurrentProjectInfo()` |
|---|---|---|
| `open('<探针>.epro')` | `{sessionId, renderId, path, headless}`，session `alive` | **空对象**（`boards: 0`、无 `uuid`、`pcbs: []`） |
| `open('<探针>.eprj2')` | 同上 | 完整（`boards: 3`，pcbs/schs 齐全） |

所以 `.epro` 不是"工程容器"，它就是一份可导入的归档；`open` 成功只说明窗口起来了，
**不说明文件被读懂了**。这条读数本身也是一条经验：`open` + session alive 不是判据。

真正能"让应用吃一个 `.epro`"的唯一门是应用内的
`eda.sys_FileManager.importProjectByProjectFile(...)`。

---

## 2 仪器：那条门怎么用（实测参数）

```
eda.sys_FileManager.importProjectByProjectFile(
    projectFile,          // 必须是 File 对象
    fileType,             // 必须是字符串 'JLCEDA Pro'
    props,                // 导入选项
    saveTo,               // 存到哪
    librariesImportSetting)
```

逐项实测结论：

- **`projectFile` 必须是 `File` 本体**。调用内部会 `structuredClone(e)`，并在分支里读 `e.name`；
  用 `{data: File}` 包裹会让主进程报
  `TypeError: Cannot read properties of undefined (reading 'match')`。
- **`fileType` 必须是 `'JLCEDA Pro'`**。传 `'EasyEDA Pro'` 会在 9 ms 内返回 `undefined`（被拒）。
  这一条踩过：早期把 `undefined` 读成"这条路不通"，其实是类型串错了。
- **`saveTo` 三种形态**：
  - `{operation:'New Project', newProjectOwnerTeamUuid, newProjectName, newProjectFriendlyName}` ← 本轮用的
  - `{operation:'Existing Project', existingProjectUuid}` ← **会把归档内容合并进那个工程**
  - `{operation:'Offline Client Local Path', folderPath}` ← 需要"扩展外部交互权限"，未启用会 throw
- **`props`** 本轮用
  `{importOption:'ImportDocument', viaSolderMaskExpansion:'cover', boardOutlineSource:'keepout',
    schematicObjectStyle:'system', associateFootprint:true, associate3DModel:true,
    importFootprintNotesLayer:true}`。

### 2.1 往 renderer 里送字节

snippet 是字符串，所以字节走 base64：把 base64 塞进 snippet（`atob` → `Uint8Array`
→ `new File([u8], name)`）。实测 108 KB → base64 122 KB、1.2 MB 也 OK
（请求帧上限 4 MiB）。

### 2.2 把应用**自己导出**的归档拿到磁盘

这是我们能拿到"有真实线段的归档"的关键：

```
eda.sys_FileManager.getProjectFile('x.epro', undefined, 'epro')
```

返回一个 `File`（`name` 变成 `x.epro.epro`，`type` 是 `'zip'`），在 renderer 里
`arrayBuffer()` 再 base64 回来即可落盘。厂商示例归档里的 `.epcb` 只有 23 B（空板），
所以我们用这个回路把**自己的探针工程**导出成 108 KB 的归档——里面正好有 2 条真实
`LINE`（`e1`、`e2`），才有东西可改。

### 2.3 回读判据（这才是判据）

```
dmt_Project.openProject(uuid)
  -> dmt_Pcb.getAllPcbsInfo()
  -> dmt_EditorControl.openDocument(pcbUuid)        // 返回 "<pcbUuid>@<projectUuid>"
  -> eda.pcb_PrimitiveLine.getAll()
```

读数单位是 **mil**（`eda.sys_Unit.getFrontendDataUnit()` 返回 `"mil"`）。

**时序坑（实测）**：`importProjectByProjectFile` 之后**同一次 invoke 内**
`openProject` + `getCurrentProjectInfo` 读到的是 `boards: 0 / pcbs: []`；
**下一次 invoke** 再探就正常（`boards: 4`、3 块 PCB）。所以不能在同一次调用里判
"导入后内容在不在"。

## 3 四臂表

写入内容选 `set_track id=e1 width_mm=0.5`：可逆、回读里一眼可辨，且 `19.685`
这个数不会与任何既有值撞车。

| 臂 | 文件 / 字节 / sha256 | `extractProjectInfo` | `import…` 返回 | PCB2 线段回读 |
|---|---|---|---|---|
| **控制臂**（应用自己导出，本模块没动） | `probe_export.epro` / 108580 B / `f339d7b09bd96a5ab6b2ab1c5255d8918f1fdaf70484471973cfbf611b9416d0` | ok，`title=pcb_agent_mcp_write_probe` | 建成工程 `d24397f2e42af86c97051ca5b1d936f69d8c50f276464f5a0778e60449c4f7ab` | **`[[2,1,21,1,0.25],[1,5,21,5,0.3]]`** |
| **写入臂**（`set_track e1 width_mm 0.5`） | `probe_written.epro` / 108443 B / `57d238c9a8fc9c94688c14bc329f0039356440e309efa26ff476452c17f444aa` | ok，同一 title | 建成工程 `0fe207c0793cbf1c06143fb61a96437346f27b052203bf2a746ed82caf652487` | **`[[2,1,21,1,19.685],[1,5,21,5,0.3]]`** |
| **负控制 A**（zip 结构合法，PCB 成员记录流换成垃圾 `["BOGUS",1,2,3]` + 坏 `LINE`） | `probe_corrupt.epro` / 95966 B / `e8ff189ad5a61784cb4b1a92e8e9f6ba1b6b205adc8d0d374a2c0ccd400f085e` | **仍 ok**（只读 `project.json`） | **仍 `ok:true`、仍建成工程** `41a715b1…`，`pcbs` 3 块 | **`[]`（线段全丢）** ← 判据会失败 |
| **负控制 B**（根本不是 ZIP：`b"not a zip at all"*100`） | — | 未测 | **`undefined`，没建工程** | — |

两条决定性读数：

- `19.685 mil = 0.499999 mm`，正是计划点名的 0.5 mm；
- **另一条没被点名的线，两边都是 `0.3`** ⇒ 唯一差异就是计划点名的那个值。

（归档总字节变小不是"内容变少"：`0.25` → `19.685` 字段变长，但 zip 是 deflate 压缩的。）

## 4 两个负控制为什么必须存在

负控制 A 是这篇的核心方法论证据：

> **一个 PCB 记录流被换成垃圾的 zip，`extractProjectInfo` 返回 ok，`importProjectByProjectFile`
> 也返回 ok，还照样建出了工程。**

所以"导入成功"和"提取工程信息成功"**都不是有效判据**——它们对坏归档不失败。
只有把 `pcb_PrimitiveLine.getAll()` 的读数拿出来，才存在一个"会失败"的判据，
而这正是负控制 A 唯一失败、控制/写入两臂都通过的地方。

负控制 B 的作用不同：它证明这扇门**确实会拒绝东西**，所以"返回 ok"不是空洞的。
两条负控制一起，把"ok"这个信号的两端都钉住了。

## 5 本轮**没有**证明的

写进代码的 `not_verified` 与 `app_acceptance.limits` 逐条对应下面五点：

1. **只对一个 app build 成立**（V4.1.60 / bridge `4.1.60.198f38ab`）。换 build 就是换仪器。
2. **只有 ZIP 容器**。`.eprj` / `.eprj2`（SQLite）仍被拒绝（`SQLITE_REFUSED`），没有任何 run 覆盖。
3. **只走了一条门**：`props.importOption='ImportDocument'` + `saveTo.operation='New Project'`。
   `Existing Project` 门在本轮把归档合并进了探针工程（多出一块"电热毯控制板"），
   `Offline Client Local Path` 门未启用权限。
4. **屏幕未核对**。所有读数都是应用自己的返回值，没人对着窗口确认。同理，
   "人看到的"与"API 返回的"是否总一致，本轮没有证据。
5. **回读的几何只有 2 条 LINE、1 块 PCB、1 份归档**。没有做多 PCB / 多文档的遍历统计。

另外两条范围外但顺带确证的：

- `.esch`（立创原理图）写路径**仍然拒写**：sheet 在 `.epro` 里，其记录布局从未对真实保存实测。
- `.eprj2` 写路径**仍然拒写**：SQLite 里板子行旁边是 `ticket` / `g_ticket` / `sort_ticket`
  和加密 `history_data`，只做 `UPDATE` 正是应用会静默当成 stale 的那种改动。

## 6 落进代码的是什么

1. `edit/epro_edit.py` 新增常量表 `ACCEPTED_ARCHIVES`（key = 容器类型）：
   表里只有**实测过**的容器，每条 run 带 `bytes` + `sha256` + `import_returned` + `lines_read_back`。
2. `_acceptance(container)` 返回条目或 `None`；`None` 不读成"被拒"，读成"没人把这个
   容器喂回过应用"。
3. `apply_plan`（以及 `propose`）返回值新增 `app_acceptance`：
   `{container, accepted_by_app, measured, read_back, control_read_back}`。
   未命中的容器 `accepted_by_app = None`，`note` 写"nothing is claimed"。
4. `not_verified` 由 `_not_verified_text()` 生成：
   - 命中表 → 给出两条 sha256、两边回读、以及**四件不覆盖的事**（换 build / SQLite 容器 /
     别的门 / 屏幕未核）；
   - 未命中 → **逐字保留旧文案**（"this archive was never opened in LCEDA Pro after the
     write…"），不静默继承新宣称。
5. `verified_by_app` **未改语义**。它说的是"这个 op 形态是厂商被观察到写过的"，
   与"应用接受这份归档"是两件事；本轮只新增了 `app_acceptance`，不把两个含义搅在一起。
   所以一个 `verified_by_app=false` 的写入，即使归档被应用接受了，也照样在
   `not_verified` 里保留那句话。
6. `tools.py` 的 `calc_capabilities → not_implemented_yet` 第 3 条与第 6 条同步改口。
7. `tests/test_epro_edit.py` 新增 `TestAppAcceptance`：断言表存在、两臂 + 两条负控制齐、
   **写入臂与控制臂的差异只在那一条线**、`19.685*0.0254 ≈ 0.5`、垃圾流回读为空、
   未知容器不宣称、未命中时旧文案逐字保留。
