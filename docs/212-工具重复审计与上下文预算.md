# 212 · 工具重复审计与上下文预算

> 发送前的一次自检：266 个工具里有几个在回答同一件事？分类折叠够不够挡住上下文被撑爆？
> 学到的东西（`data/` 里的十一张表、经验种子）是不是真的随项目一起发出去了？
>
> 三条都要**当场量**，不能凭印象。本文记方法、读数与结论，下一次发版可以照着重跑。

## 1 功能重复：0 组

判据分四层，每层都可以单独变红，所以"没重复"不是一句印象：

| 层 | 问题 | 读数 |
| --- | --- | --- |
| A | 有没有两个名字挂在同一个 handler 上（同一份代码两个入口） | **0 组** |
| B | 有没有两条 description 逐字相同（复制粘贴出来的第二份说明） | **0 组** |
| C | 名字相似度 ≥ 0.72 / ≥ 0.80 的对有多少 | **199 / 45 对** |
| D | 这些对里，描述两两 Jaccard ≥ 0.55 的有几对 | **0 对**（最高 < 0.55） |

C 层的数字大是因为工具名共享前缀（`board_nets` / `board_zones` 的字符相似度就很高），
名字像不等于做同一件事，所以真正要读的是 D 层：**没有任何一对工具的描述在讲同一件事。**

另有一层只能靠读：

**参数签名（`properties` + `required`）完全相同的有 9 组**，逐个读到判词：

| 组 | 判词 | 依据 |
| --- | --- | --- |
| `creepage_required` / `clearance_required` / `spacing_required` | disjoint | IEC 60664-1 的三个不同输出（沿面 / 穿空气 / 同时给两个），同输入不同量 |
| `board_summary` / `board_topology` / `board_reservations` / `board_zones` | disjoint | 计数与叠层 / 功能块拓扑 / 规则区 / 实际灌注的铜，四件不同的事 |
| `pcb_rule_catalog` `board_ops` `schematic_ops` `part_cache_info` `experience_status` `pattern_status` `calc_capabilities` `jlc_library_validate` | disjoint | 八个**只吃零参数**的目录类工具，各自列自己的目录 |
| `board_width_ladder` / `board_via_ladder` | disjoint | 线宽阶梯 vs 孔尺寸阶梯（环宽约束把两个数耦合起来，所以是两套算术） |
| `match_pi` / `match_t` | disjoint | π 网络（低通形式）vs T 网络（高通形式），互为对偶 |
| `board_propose` / `schematic_propose`；`board_apply` / `schematic_apply` | disjoint | 板与原理图两条写路径，格式不同、门禁不同 |
| `layout_review` / `schematic_review` | disjoint | 布局规则集 vs 缺失元件/隔离间距核查 |
| `board_rules` / `board_stats` / `schematic_hierarchy` | disjoint | 网络类解析 / KiCad 自己的统计 / 原理图文件层级 |

名字最像、最像"重复"的几对，描述的边界都写在正文里：

- `diff_impedance`（闭式）vs `diff_impedance_field`（场解）——同一个问题两种答案，谁都说清自己是哪种；
- `board_zones`（读文件里**已经**铺好的铜）vs `board_fill_zones`（调 KiCad 自己的 `ZONE_FILLER` 去铺）；
- `fusing_current`（等温、显式删掉散热）vs `fusing_current_taper`（轴向分段 + 节点导热，`fusing_current` 删掉的那个长度轴）；
- `magnetics_core_loss`（你给系数）vs `magnetics_material_core_loss`（厂商目录的系数）vs
  `magnetics_core_loss_audit`（拿你的三元组去撞厂商**印出来的** 17 个 PV 点，并且明确拒绝反解系数）。

**结论：没有可合并的工具，也没有应当退役的。** 266 个里每一个的"我算什么、我不算什么"都写在它自己的描述里，
合并只会把两条不同的失败方式糊成一条。

## 2 分类折叠：三档，实测字节

机制（`tools.py` 的 `DEFAULT_TOOLSET` / `_resolve_toolset` / `tools_page`）：
默认 `core`、`PCB_AGENT_TOOLSET=all` 全量、`<tokens>` 按名字或前缀自选（`core` 可混写），
任何档位都强制追加 `tool_search` / `tool_call` 两个 meta 工具——否则被过滤掉的工具就再也够不着了。

实测（`0.1.42`，默认 25 KiB 单页预算，字节数是**整条 JSON-RPC 回复**）：

| 档位 | 工具数 | 页数 | 字节 |
| --- | --- | --- | --- |
| 默认 `core` | 50 | 1 | 24 847 |
| `board_` | 87 | 3 | 72 091 |
| `lceda_` | 19 | 1 | 19 209 |
| `magnetics_` | 14 | 1 | 21 475 |
| `jlc_` | 14 | 1 | 13 104 |
| `schematic_` | 13 | 1 | 10 366 |
| `experience_` | 11 | 1 | 11 570 |
| `vibration_` | 10 | 1 | 18 932 |
| `antenna_` / `filter_` / `match_` / `pattern_` / `thermal_` | 9 各 | 1 各 | 7 935 / 14 108 / 6 255 / 8 660 / 10 608 |
| `all` | 266 | 7 | 170 677 |

三档够用的理由，按数字：

- **默认一页 24.8 KB**，聊天客户端在第一条用户消息之前付的代价是固定的、且小于一次正常对话；
- `core` 已经顶到 25 KiB 预算（约 750 B 余量），所以 JLCPCB 制板门禁（12 个）、`board_netlist`、
  `board_sim` **刻意不在 core 里**——它们留在注册表、由 `calc_capabilities` 列出、用
  `tool_search` / `tool_call` 取到。加进去就得挤掉一个已有入口；
- 想扩也**不需要新机制**：任意前缀自选，最大的 `board_` 也只 3 页 72 KB，比全量省 58 %；
- 纯中文查询由 `_CJK_ALIASES` 别名表接住（阻抗 / 过孔 / 铺铜 / 散热 / 爬电…），
  表里没有的词明确回「这次什么都没搜，改用英文关键词」而不是安静地回零条命中。

**发现的一个真问题在折叠之外**：`calc_capabilities` 被开通首上手指令成"先调我"，
而它自己的完整自述是 **70 586 B**（超过 48 KB 单条上限，会被截断并落盘）。
也就是说「省上下文的入口」本身是最大的一笔开销之一。本轮给它加了 `shipped_data`（见 §3），
但没有改它的默认形状——改默认会动所有既有调用方的读数，属于另一次决策。

## 3 经验与数据表：随项目发出去

十一张表在 `data/`（仓库根，不在包里）：`creepage_tables` `iec60664_tables` `ipc2152_tables`
`magnetic_materials` `powder_cores` `powder_curve_fits` `toroid_mlt_reference`
`material_loss_anchors` `dc_bias_fit` `layout-rule-sources` `experience_seed`。

### 3.1 两个真缺口

1. **`pip install` 的 wheel 里一张表都没有。** `pyproject.toml` 只声明了 `pcb_agent_mcp.jlc` 的
   package-data，根 `data/` 既没 package-data 也没有 `MANIFEST.in`，而七个模块按「仓库根 / data」硬算路径。
2. **经验种子缺失时静默回空库。** `experience._read_seed()` 吞掉 `OSError/ValueError` 返回 `[]`，
   `experience_status` 于是读成「随包的库是空的」——"文件不在这台机器上"和"库是空的"是两件事，
   前者是环境问题，后者是对语料的判断，混在一起就是错答案。

### 3.2 修法

- 新增 `src/pcb_agent_mcp/datafiles.py`：按
  `<PCB_AGENT_DATA>` → 仓库 `data/` → 包内 `data/` → `<prefix>/share/pcb_agent_mcp/data/`
  顺序找**文件**（不是找目录），先找到的胜出；`find()` 找不到回 `None`，`require()` 抛
  `MissingTable` 并在消息里列全搜索过的路径；`report()` 报「找到几张 / 缺哪张 / 找过哪几个目录」。
  六个 calc 模块 + `experience.py` 全部改走它。
- `pyproject.toml` 增加 `[tool.setuptools.data-files]`：`"share/pcb_agent_mcp/data" = ["data/*.json"]`。
  构建实测：11 个 JSON 全部进 wheel，装好后落在 `<prefix>/share/pcb_agent_mcp/data/`。
- `experience._read_seed(diag=None)`：缺文件时把 `seed_found: false` 与 `seed_note`（路径 + 异常）
  带回去，`library()` / `status()` 在缺失路径上加这两个键、`status.message` 直说「种子**没找到**」。
  **文件存在时输出逐字节不变**——新键只在缺失路径上出现，这是"健康答案不变"的守门方式。
- `calc_capabilities` 增加 `shipped_data`（就是 `datafiles.report()`）：让「这台机器上这套能力全不全」
  成为读数，而不是等某个工具报 `SAFETY_TABLE_MISSING` 才知道。

### 3.3 分工写死

| 东西 | 在哪 | 谁写 |
| --- | --- | --- |
| 经验种子（7 条 active，量自 20 块真实板） | `data/experience_seed.json`，**只读** | 随包发出，本机永不改 |
| 本机学到的条目 / 观测 | `$PCB_AGENT_HOME/experience.json`（默认 `~/.pcb_agent_mcp/`） | 运行时写；同 id 会 shadow 种子并**当场报告** |

## 4 本轮改了什么

- `src/pcb_agent_mcp/datafiles.py`（新增）、六个 `calc/*.py` + `experience.py`（路径与缺表语义）、
  `tools.py`（`shipped_data` + 折叠层注释里过时的 `~190 tools / ~315 KB / 46 / 23 976 B` 改成实测值）、
  `pyproject.toml`（data-files）、`README.md`（折叠三档实测表、"随包的数据表与经验语料"节、48 KB 段的当轮实测）、
  `CHANGELOG.md`（Unreleased）、`tests/test_datafiles.py`（8 例）。
- 工具数 **266 → 266**；`--selftest` **366/366**；`tests/test_datafiles.py` 8 例全绿。
- 未做：`calc_capabilities` 的默认体积（70 586 B）未压缩，只加了 `shipped_data`；
  没有把表搬进包里（`docs/` 全按 `data/` 这个路径写，搬一次要改几十处提示文案，收益只是少一条搜索路径）。
