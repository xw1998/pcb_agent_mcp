# 26 看得见、打得断、填得实：一轮把「不可观察」改掉

这一篇记的是**第一次真的按流程画一块板之后**暴露出来的问题，以及修复它们时推翻的四个
自家结论。触发点是两句用户原话：

> 「绘制原理图与pcb过程不能看到你一步一步怎么做的在EDA界面上看不到不好给你建议和打断，
> 还有就是立创eda不支持你联网查器件直接用」

两句话其实是同一件事的两面：**工具做完了事但过程不可观察**。前一句是「写」不可观察——
一次 `apply` 从「改前」直接跳到「改后」，人看着 EDA 窗口什么也没发生，没法在第 17 步喊停；
后一句是「读」不可观察——模型拿不到真实器件，只能编一个封装。加上一轮「这 MCP 有哪些不足」
的自审，这一篇覆盖六件事：

| § | 改了什么 | 它推翻了什么 |
|---|---|---|
| 26.1 | 分步写（`steps_apply`）+ 进度/停止/续跑 | 「apply 必须是原子的」——原子是给脚本的，不是给协作者的 |
| 26.2 | 器件库与在线检索（`parts.py`，6 个工具） | 「要真实器件只能手抄」；同时推翻「立创的库是加密专有格式」 |
| 26.3 | DRC 分级（`edit/drc_policy.py`） | 「有 violation 就挡」——真板 69 条全是 warning，挡完就没法编辑 |
| 26.4 | `board_routability`：几何逃逸通道 | 「栅格能回答 pad 出不出的去」——0.5 mm 间距下栅格必然假警 |
| 26.5 | 叠层总厚：声明 1.6、实际 1.18 | 「写了 `(general (thickness 1.6))` 就是 1.6 mm」——KiCad 只累加 stackup |
| 26.6 | 铺铜闭环（`fidelity/fill.py`） | 「`add_zone` 之后那块铜就算有了」——没有 `filled_polygon` 就只是个轮廓 |

## 26.1 分步写：把「一次跳变」拆成「可观察的块」

### 26.1.1 一次 `apply` 为什么不可观察

`apply_plan` 的形状是对的：checkpoint → 原子写 → 五道闸门 → 回滚。但对**协作者**是错的：

* 文件在磁盘上从「改前」一步跳到「改后」，中间的树从没存在过，EDA 窗口没有可刷新的时刻；
* 用户看见的第 1 步和第 37 步之间没有任何时机能评论；
* 一旦想停，只能整份放弃。

这不是「要不要好看的进度条」，而是**用户的建议与打断无处落地**。所以拆成块，但**不降低证明
义务**——这是这一节的全部设计约束。

### 26.1.2 契约（板与原理图共用一套代码）

`plan.py` 里 `STEPS` 会话，磁盘是真相：

| 产物 | 位置 | 作用 |
|---|---|---|
| 快照 | `<home>/steps/<plan_id>/<seq>.kicad_pcb` | 每块写完后**完整合法**的文档 |
| 事件 | `<home>/steps/<plan_id>.jsonl` | 一列一行的进度账，进程死了也在 |
| 停止 | `<home>/steps/STOP` | 块间被检查；命中即 `STOPPED_BY_USER`，计划不消耗 |
| 续跑 | `step_control(status|stop|resume)` | `resume` 用 `shutil.move` 归档 STOP 文件 |

每块的动作固定为：**重读磁盘 → sha256 与计划里的 `sha256_before` 比对 → 只跑这一块的
`run_all(subset, seed_base, index_offset=lo)` → `_atomic_write` → 写快照 → 重新解析验后置
条件 → 追加一行 JSONL**。「重读再比」是硬要求：块与块之间人可能在编辑器里改过，这时**该块
必须拒绝**（`FILE_CHANGED`），而不是拿计划里的旧字节盖掉它。

末块照跑完整闸门，其中一道是**分步结果 vs 一次性结果**的等价性检查——这是「分步没有悄悄变成
另一件事」的唯一证据。

### 26.1.3 一个只有分步才暴露的真 bug：uid 依赖调用次数

原理图的 op 生成 uid 时用了「本次调用里已造了多少对象」作计数器。一次性 apply 时，第 5 个
op 看到一个数；分步时每块都从 0 开始，同一个 op 看到另一个数——于是**同一份计划分步与一次
性产出不同的 uid**。修法是把计数器在每个 op 之前显式归零（`sch_ops.run_all` 里 `ed._n = 0`），
让 uid 只取决于 `seed_base + op 下标 + op 内序号`。这条如果不修，等价性闸门会红，但人会以为
是浮点/排序噪声——**这类 bug 只在「把同一件事分两次做」时才现形**。

### 26.1.4 立创 Pro 那一侧：写路径一次都没跑过

`lceda_pro_steps` 走进程内桥（见 24 篇）。本机**从非交互会话启动不了 `lceda-pro.exe`**
（数秒即退，`available_endpoints() == []`，`connect()` 抛 `APP_NOT_RUNNING`），所以它的
真机验证是**欠账**，只能靠单元测试与假 transport 证明失败路径。这条在诚实清单里明写。

## 26.2 器件库与在线检索：先证明库里有什么，再决定能说什么

### 26.2.1 离线库不是二进制黑箱

`<LCEDA Pro>/resources/app/assets/db/lceda-std.elib` 有 461 MB，但前 16 字节是
`SQLite format 3`。实测结构（2026-10-29，本机）：

| 表 | 行数 | 里面是什么 |
|---|---|---|
| `devices` | 16 828 | 器件（一个型号一行） |
| `components` | 21 310 | 文档：`docType 2` = 符号，`4` = 封装 |
| `attributes` | 384 775 | `Manufacturer Part` / `Supplier Part`（= 立创编号）/ `Supplier Footprint` / `Datasheet` / symbol uuid / footprint uuid … |
| `device_fts_inv_idx` | —— | 倒排索引，`part_search` 用它 |

符号与封装几何在 `dataStr` 列：**EasyEDA 自己的逐行文档格式**，一行一个 JSON 数组，
坐标单位写在 `["CANVAS",…,"mil",…]` 那一行里。实测全库 3 911 个文档写 `mil`、131 个写 `mm`、
2 个什么都没写——**没写的一律拒绝**，不去猜单位：0.0254 的错就是 39 倍的焊盘间距错误。

### 26.2.2 在线检索能查、不能取几何

`POST https://pro.lceda.cn/api/v5/devices/search`，body `{"wd": "..."}`。匿名（无 cookie、
无 token）即 200，覆盖整个嘉立创/立创商城目录（2026-10-29 实测 `count` = 1 613 360）。

它**不给几何**：组件记录只有 `dataStrId` + `iv` + `key`，文档在 `modules.lceda.cn` 上加密
下发。所以 `part_search` / `part_get` 对库外器件回 `geometry: "not_offline"`，**绝不编一个
封装**——这正是用户那句「不支持你联网查器件直接用」的技术真相：能查的查得到，能画的只在
本地库里。

### 26.2.3 六个工具与一条诚实边界

`part_library_status` / `part_search` / `part_get` / `part_export` / `part_footprint_pads` /
`part_cache_info`。边界写在模块 docstring 里并原样进 `precision`：

* 符号文档没有 `CANVAS` 行，它的比例是从**引脚间距**反推的（引脚落在 10 单位栅格，
  10 × 0.254 mm = 2.54 mm 复现标准 100 mil）；
* 旋转焊盘的**角度符号约定**只在对称焊盘（0°/90°）上对过，非对称旋转多边形没有和 app 自己
  的渲染逐像素比过；
* EasyEDA 的 49/50/51 层（`COMPONENT_MARKING` / `PIN_SOLDERING` / `PIN_FLOATING`）在转换里
  **丢掉**，因为 KiCad 从焊盘自己推 mask 与 paste。

## 26.3 DRC 分级：把「有 violation 就挡」换成「按厂商自己的严重度」

真板上 69 条 violation 全部是 warning：`text_height` 32 / `silk_over_copper` 21 /
`silk_overlap` 14 / `silk_edge_clearance` 2。原来的闸门「有新增 violation 就回滚」意味着
**这块板永远改不动**——而不能编辑不是安全属性。

`edit/drc_policy.py`：

* `BLOCKING_SEVERITIES = {"error"}`；
* 读不到 severity ⇒ **fail closed 阻断**（信息缺失不能变成放行）；
* `classify()` 给 `policy / strict / total / by_severity / blocking_total / advisory_total /
  blocking / advisory`；`HINTS` 给每种类型一条修法；
* `board_drc` 与两处 apply 闸门改判 `new_blocking_total`，`options.strict_drc` 可一键回到
  「warning 也算墙」——闸门的牙齿没拔，只是默认不再咬自己的手。

`tests/test_edit.py` 里那条老测试原本断言「边缘丝印被挡住」，现在改成两条：默认**落地并
报告为 advisory**，`strict_drc` 下**确实回滚**。改测试而不是改代码，因为原来的断言在真板上
等于要求「这块板不可编辑」。

## 26.4 `board_routability`：栅格回答不了 0.5 mm 间距的 pad

### 26.4.1 第一版错在哪

第一版用占用栅格：`free` / `occupied` / 板外。它把 180 个 pad 全判成「永远连不上」，三个
叠加的根因：

1. `fp.get("reference")` —— 键名是 `ref`，`reference` 恒 `None`；
2. 外框被展平成点列表后传给 `point_in_polygon(pt, 点)` ⇒ 每条走廊都判为出板；
3. 栅格是**纯布尔**、不带网属 ⇒ pad 永远被自己的铜包围。

第三条不是实现 bug 而是模型错：栅格能表达「哪块地被占」，表达不了「0.5 mm 间距的两个 pad
之间还有 0.225 mm 余量，所以 0.25 mm 的线出得去」。而 pad 能不能出去**恰恰就是这个余量的
比较**。QFP-100 上 0.325 mm 的 margin 让每个 pad 的光晕吞掉邻居，78/180 被判死刑。

### 26.4.2 现在的判据：几何走廊 + 精确距离

* 每个 pad 试 8 个方向（4 正 4 斜，斜向按 0.7071），走廊 = 从 pad 边缘向外 `escape_mm` 的
  一条带宽度的线段；与**其它网**的铜皮做 `_dist` 精确距离比较，同网铜皮不算阻挡；
* keepout 用 3 点采样、外框用 5 点探针（中心线 3 点 + 远端两肩）；
* 性能：`_bucketize` + **bbox 间隙下界**（真实距离 ≥ `hypot(gap_x, gap_y)`）先筛，
  真板 180 pad / 4 层从 14 s 降到 **3.3 s**；
* 栅格只留作 congestion 的度量，并且改成**带网属**的栅格（`False` 空 / `None` 板外 /
  网名字符串 / `True` 多网或 keepout）。板外不再计入分母——这一条曾让 congestion 从
  0.4153 虚高到 0.7556。

### 26.4.3 三态判词，而不是「能/不能」

| 判词 | 含义 | 为什么要分开 |
|---|---|---|
| `blocked_pads` | 连 `short_escape`（0.2~0.4 mm）的短走廊都出不去 | 这是**任何布线器都救不了**的硬卡，PCB 必须改 |
| `bends_needed` | 长走廊全堵、短走廊能出 | 直线扇出不行，**人拐个弯就行**；混进 hard 里就是假警 |
| `escapes_exist` / `tight` | 有通路 | —— |

失败要给可执行信息：`why_blocked` 报「被谁挡（`net` / `reference`）+ 类别 + 还差多少 mm
（`needs_mm = clearance − 实际距离`）」。已经连着同网 track/via 的 pad **永不进 blocked**
（判据：pad 中心到同网 track/via 中心线距离 ≤ `half + w/2 + 0.06`）——工具要回答「哪里卡住」，
把已经连好的 pad 报成「没人能连」是假警。

真板实测（`_scratch/core/stm32f401re_core.kicad_pcb`，32 封装 / 194 pad / 0 track）：
`verdict = bends_needed`、`pads_checked = 180`、`blocked = 0`、`bend_required = 1`
（U4 的 SOT-23-6 第 5 脚 VBUS）、`one_way = 11`、congestion F.Cu 0.4153 / In1·In2 0.191 /
B.Cu 0.195、耗时 3.3 s。空板（无带网 pad）直接 `err(NO_GEOMETRY)`，不给 `0 个堵` 这种答案。

`model = "geometric_escape_lane + rasterised_congestion"`，且 `assumptions.not_claimed`
里写死：**这不是路由，只说 pad 能出去。**

## 26.5 叠层总厚：文件说 1.6，实测 1.18（根因级）

`create_board` 写 4/6 层板时的介电层分配是 `each = (thickness − 0.07) / (inner + 1)`，
但只写 `inner` 层介电：声明 1.6 mm 的 4 层板叠层实加 **1.18 mm**。而 KiCad 的 `stats`
**只累加 stackup、忽略 `(general (thickness …))`** ⇒ 引擎报 1.18。也就是说：**这个工具造出来
的每一块多面板，文件说的厚度和实际造的厚度都不是一个数**，而所有闸门都绿着。

两处一起错：

1. 铜 + 阻焊的预算按 0.07 mm 计（4 层是 4 × 0.035 + 2 × 0.01 = 0.16 mm）；
2. 介电预算除以 `inner + 1`，却只写 `inner` 层——而物理叠层是**每两个铜层之间恰好一层介电**，
   n 层铜需要 n − 1 层介电。

修法：`n_dielectric = copper_layers − 1`，`dielectric_total = thickness − 0.035·n_cu − 0.02`，
每层 `dielectric_total / n_dielectric`，然后按「铜 → 介电」交替写出。

修完还要**防回归**，于是把它变成闸门：`engine_stats` 新增三字段
`thickness_stated_mm` / `thickness_engine_mm` / `thickness_agrees`（容差 0.005 mm），
`agree is False` 直接 `engine_stats.ok = False` ⇒ 创建失败、删文件、抛 `GATE_BLOCKED`。
读侧同样补上：`board_summary` 的 `thickness_from_stackup_mm` 与 `thickness_agrees`，
这样**不跑 KiCad 也能看见**「文件说 1.6、叠层只有 1.18」。

`tests/test_stackup_thickness.py`：2/4/6 层 × {0.8, 1.2, 1.6} mm 全矩阵断言
`general.thickness == stackup 累加`；再从外部把 `(thickness 1.18)` 替换进去，断言
`thickness_agrees` 变 false（生成器帮不了这个忙）；没有 stackup 时返回 `None` 而不是猜。
`PCB_AGENT_ENGINE_TESTS=1` 才跑 kicad-cli 那一对（它的 round trip 在本机是分钟级）。

真机复验（`kicad-cli 10.0.7`）：2 层 1.6 / 4 层 1.6 / 6 层 1.2 / 4 层 0.8 / 6 层 1.6 全部
`board_thickness` 与声明**逐位相符**。

## 26.6 铺铜闭环：没有 `filled_polygon` 的 zone 只是一条轮廓

### 26.6.1 欠账是什么

`add_zone` 写下 zone 轮廓与 `(fill yes)`，回复 `fill_pending: true`，然后
`board_pour_connectivity` 会说 `outline_only`。于是之后所有关于铺铜的问题——连通性、
Gerber 铜皮、`zone_fill` 标记——**答的都是轮廓**。这正是「中间转换层说一套、真板是另一套」
的那种失败，只是它藏在一个布尔标记后面。

铺铜不可能由我们自己算：pour 取决于 clearance、热焊盘辐条、孤岛去除、板框缩进。所以像 DRC
一样**委派**：KiCad 自带 `pcbnew` Python 模块，里面有 `ZONE_FILLER`。

### 26.6.2 两种写，故意分开

| 调用 | 做了什么 | 谁的文件被改 |
|---|---|---|
| `board_fill_zones(path)` | 在**临时副本**上跑 `ZONE_FILLER`，报出会铺出多少铜、哪些 zone 一点没铺、为什么 | 谁都没动 |
| `board_fill_zones(path, in_place=true)` | 把 KiCad 产出的 `filled_polygon` 节点**移植**进原文件，先写 checkpoint | 原文件，可回滚 |

为什么不是「让 pcbnew 存一遍」：`SaveBoard` 会**把整块板重写成 KiCad 10 的排版**，还会把
`(version 20221018)` 升成 `(version 20260206)`、把 `(generator pcb_agent_mcp)` 改成
`(generator pcbnew)`。用户没要求重排他的文件。所以只搬节点：按 zone 顺序 + `net` + `layer`
三重校验后，删掉旧的 `filled_polygon`、插入 KiCad 那几棵**逐字节解析出来的**子树
（`dumps_verbatim` 保留原始 trivia），其余字节一个不动。移植后再重新解析，要求多边形数与
写进去的一致，否则**回滚原字节**并报 `VERIFY_FAILED`。

实测：1749 B → 2165 B，`(version 20221018)` 与 `(generator pcb_agent_mcp)` 原样保留，
我们的适配器把 `zone_fill` 标成 `present: true`，KiCad 自己的 DRC 能解析这份移植后的文件
（一块无 pad 的板上它报 1 条 `isolated_copper` warning —— 铺出的铜没连任何东西，这正是真话）。

### 26.6.3 写路径里的闭环

`board_apply(..., fill_zones=true)`：计划写完之后、闸门判决之前，跑一次 `fill(..., in_place)`
并记为 `zone_fill` 闸门。**填不成就是失败**，不是脚注——请求了闭环却悄悄只留轮廓，就是假绿。
闸门里同时写死两条：

* `drc_rechecked: false` —— 上面那次 DRC 比对发生在铺铜之前，**它描述的不是这块铜**，
  要判铺完的板请再调 `board_drc`；
* 铺铜是**快照**：之后任何 track / pad / 板框改动都会让它过时（KiCad 的「重新铺铜」同理）。

keepout 由引擎自己兑现：往里加一个 10×10 的 keepout，铺铜面积少掉 ~100 mm²，这个数在
`tests/test_zone_fill.py` 里被断言（不是「相信引擎」而是「量引擎」）。
