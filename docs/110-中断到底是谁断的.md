# 110 · 「又中断了」到底是谁断的：证据、判据与 0.0.110 改了什么

> 用户的原话是「mcp还是有问题，又中断了」。上一版（0.0.109）已经把 `tools/list`
> 和 `--selftest` 的出口量过一遍，所以这一次不能再拿「修过了」当结论，也不能反过来
> 拿「MCP 没问题」当结论 —— 两边都要有读数。

## §1 先量 MCP 自己的出口：这一侧现在没有任何一条超预算

真起一个 stdio 会话（`initialize` → 各方法 → `tools/call`），逐条数字节：

| 方法 | 应答字节 | 说明 |
| --- | ---: | --- |
| `initialize` | 624 | 含 `instructions` |
| `ping` | 38 | |
| `resources/list` | 52 | |
| `prompts/list` | 50 | |
| `resources/templates/list` | 60 | |
| `tools/list`（core，默认档） | 37 210 | 46 条，一页，无 `nextCursor` |
| `tools/list`（伪造 cursor） | 37 210 | 不报错、不叠页，重发第 1 页 |
| `no/such/method` | 95 | `-32601` |
| 批量数组 `[ping, tools/list]` | 37 250 | 回数组，不炸连接 |
| `tools/call tools_help` | 217 | |

结论：**MCP 这一侧没有任何一条应答超出预算**，`tools/call` 的 48 KiB 闸门与
`tools/list` 的分页都在岗。所以「又中断了」不能归到「MCP 发得太大」上 ——
至少 0.0.109 之后不能。

## §2 再看宿主自己的日志：死亡签名是模型流，不是工具

宿主日志 `%APPDATA%\WPS 灵犀\logs\app-server\app-server_2026-11-03.log`
（当天 20 302 行）。按 `level=error` 找，当天有 **113 次**

```
msg=AIGCFailed ... err="empty choices" model=deepseek-v4.1-flash-1017
```

分布在 5 个不同会话上（本仓库会话 `12035378791710893` 只是其中之一），按小时：

```
00:1  06:3  09:53  11:3  12:16  13:26  14:2  15:7  17:2
```

09 点那一坨 53 次是重灾区。紧随其后必有

```
msg="run terminal outcome classified" component=run
err="agent run: empty choices" error_kind=internal
```

当天 19 条 `run terminal outcome classified`，其中 17 条就是
`agent run: empty choices`。

还有 1 条形态完全不同，值得单独记住：

```
2026-11-03T12:40:20  err="agent run: [18] compact failed: [18] compact failed"
```

**同一会话（本仓库）当天断了三次**：12:32:33（empty choices）、12:38:00
（empty choices）、12:40:20（**compact failed**）。也就是说：对话长到要压缩时，
压缩这一步本身也是一次模型调用，它也吃 `empty choices`，于是压缩失败，run 直接
判死 —— 这就是之前那句「网络异常 → 压缩失败 → 对话过长」的机制。

## §3 判据与不许读成的东西（重要）

判词：**「中断」= 上游模型通道返回空流（`empty choices`），run 被判死；
MCP 这一侧不是发起者。**

必须一起写死的三条限定，否则这条判词会被读过头：

1. **日志里没有请求体积字段。** 我找过 `prompt_tokens` / `usage` / `body_bytes`
   —— 一条都没有。所以「体积大到超上下文 ⇒ 上游回空流」这个链条在本证据下
   **不成立也不被否证**，只能记成未定。不许把它写成「因为 MCP 发得大所以断了」。
2. **跨会话同签名**说明它不是本仓库 MCP 专属：补天会话、其它项目会话同样中招。
   一个只在装了本 MCP 的会话里出现的故障，才叫「这个 MCP 的问题」。
3. **压缩失败那条是宿主的路径**，MCP 无法插手；能插手的只有「让它晚一点需要压缩」。

## §4 那 MCP 还能做什么：把每轮都在付的那笔钱降下来

`tools/list` 只在挂 connector 时拉过（当天日志里就两次 `[connectors] ... list tools
result`），但**工具定义会作为函数声明进入每一次模型请求**。所以 37 210 B 不是
「一次性的读取成本」，而是每一轮都付的约 11 000 tokens —— 对照 5.7 万 tokens 的
压缩底板，占约 19 %，而且是纯散文。

0.0.110 改的就是这笔钱，做法与 0.0.109 一脉相承：**先削文，不动条目**。

原来裁剪只有一个档（顶层描述 200 字 / 参数描述 80 字）→ 38 766 B，之后再放不下
就只能分页。而**分页对不跟 `nextCursor` 的宿主等于丢工具**，不能拿它当默认档。
所以加一条阶梯，从「文本最全」往「只剩 schema」走，挑第一档能一页装下的：

| 档位（顶层/参数 字数） | core 46 条 |
| --- | ---: |
| 全量 | 54 905 B |
| 200 / 80（0.0.109 唯一档） | 38 766 B |
| 120 / 40 | 33 396 B |
| 120 / 0 | 26 725 B |
| **60 / 0（0.0.110 默认档停在的）** | **23 976 B** |
| 0 / 0（描述退化成 `...`） | 21 222 B |
| 全部描述删除 | 15 127 B |

最后一行是关键：**schema 本身的地板是 15.1 KB**。任何低于 ~16 KiB 的预算都只能靠
砍工具来满足，而砍工具正是这个文件存在的理由的反面。所以默认预算定 **25 KiB**：
一页装得下全部 46 条，1.55 万个参数名/类型/枚举/必填一个不动，只把散文缩到每工具
60 字。默认应答 37 210 → 23 976 B（**−36 %**，约省 3.7k tokens/轮）。

新增的环境变量与语义：

| 变量 | 默认 | 语义 |
| --- | --- | --- |
| `PCB_AGENT_MAX_TOOLS_KB` | `25` | 一次 `tools/list` 应答的预算；`0` = 不限（还原 0.0.109 之前那种全文） |
| `PCB_AGENT_MAX_RESULT_KB` | `48` | 一次 `tools/call` 应答的预算（**没变**，与上一条分开） |

应答里多三个字段，只在真的削过时出现：`descriptions_shortened`、
`prose_cut`（`"60/0"` = 顶层 60 字 / 参数 0 字）、`fields_shortened`（被截断的
字段个数，默认档 265 个）。

## §5 反向对照（每条都能真红，红过才算数）

自检里新增两条，加上 0.0.109 已有的四条（已改用新变量名）：

1. **默认档一页装得下 46 条**，且 `nextCursor` 不出现 —— 把默认预算写成
   20 KiB 就会红（20 KiB 时连 `0/0` 的 21 222 B 也放不下，会退化成 4 页）。
2. **压到 8 KiB 必须分页且一条不丢**：逐页累加后名字序列与全量逐位相同、
   无重名、每页 ≤ 8 KiB。
3. **`=0` 必须逐字节等于旧答案**：`json.dumps(page) == json.dumps(raw)`，
   且不带 `descriptions_shortened` —— 这一条挡的是「悄悄改了 schema」。
4. **`all` 档（190 条）在 25 KiB 下仍能靠游标走完**，且每页不超预算。
5. **削的只能是散文**（0.0.110 新增）：默认页里 46 条工具的
   `properties` 名集合、`required` 列表、**每个 `enum` 的值**都与未裁剪的
   spec 完全相同。判定用三元组指纹比对，差异列表非空即红。
6. **抬预算必须真的把散文还回来**（0.0.110 新增）：`=0` 时字节数必须大于默认页、
   且 `fields_shortened` 不出现 —— 挡的是「省下来的 13 KiB 其实是从别处减的」。

## §7 欠账（登记不擅自做）

1. **`349 checks` vs `350/350 passed` 的显示差 1**：`---- N checks` 这一行在
   最后那条「闸门自己没变慢」的棘轮自检**之前**打印，所以它数的是 N−1。属读数
   层瑕疵（计数位置），不影响判定，下一轮把统计挪到收尾一起修。
2. **真宿主是否跟 `nextCursor` 仍未验证**（0.0.109 起就登记了）。所以默认档的
   设计前提是「一页装下」而不是「分页也行」；这条没验证之前，不许把默认预算
   降到需要分页的档位。
3. **体积 → `empty choices` 的因果未定**（见 §3.1）。要定它需要宿主侧记录请求
   字节数或 token 数，这不是本仓库能拿到的读数。
4. **压缩底板 5.7 万 tokens 里，本 MCP 现在约占 6.6k（23 976 B）**。再往下压只能
   动 schema 地板（15.1 KB）或减工具数 —— 后者要用户点头，且会改变能力面。
