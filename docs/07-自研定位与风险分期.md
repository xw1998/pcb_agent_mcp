# 自研的定位、双栈约束、风险排序与分期

日期：2026-10-27
状态：**规划阶段**。本文只定方向与切法，不含实现细节。

前置：00~06 篇。本文是它们的收敛结论——00 讲生态位、01 讲表示、02 讲占用与经验、03 讲丢失、04 讲布局、05 讲无损架构、06 讲存储现状与现有 MCP 的实际信息量。**06 证明了缺陷存在，本文回答"那我们要做什么、按什么次序做"。**

**本版修订（相对初稿）：取消"第一版只接 KiCad"的方案。立创 EDA Pro 与 KiCad 双栈是必备能力，不允许只做一个。** 详见 §3、§4。

---

## 1. 先把名字改对：我们要做的不是「转换工具」

「把 PCB 文件转成 AI 能读的东西」这个说法会把预算算错，因为**转化本身已经不是门槛**：

| 已有能力 | 归属 | 说明 |
|---|---|---|
| EasyEDA Pro → KiCad 格式 | KiCad 官方 | 官方已实现 EasyEDA Pro 导入器；`.epcb` 行类型的权威说明就出自它的文档 |
| 立创在线读写 | 官方 `run-api-gateway`（Apache-2.0） | 读写接口现成，配 `easyeda-api` Skill 作文档加速器 |
| KiCad 读写 | `pcbnew` / S-expr 解析 | 几十年老代码，格式稳定 |

所以工作量分布是：

```
读文件 + 建对象模型   ≈  5%
从图元推导事实        ≈ 95%
```

**结论：这是「推导工具」，文件解析只是它的输入侧。**
自研的必要性不来自"没人会解析"，而来自"没人把解析结果算成事实"——这正是 06 篇 §5 的核心发现：现有 MCP 的返回形态只有布尔回执 / 单图元裸 JSON / 人写摘要三种，**没有第四种（派生事实）**。

### 1.1 为什么现有工具做不到，而不是不想做

不是作者疏忽，是协议层决定的：

- MCP server 是终端，**模型没有「板子」这个可反复观察的对象**，只有「调一次 → 拿一段文本」；
- tool 面以图元为单位时，模型布线一次只能拿到一个布尔值，**失败原因不可见** ⇒ 只能换坐标重试 ⇒ 盲搜，不是设计；
- 把图元聚合成人写摘要（形态 C）会丢精度且无法反查，正是 05 篇推翻的那条路。

⇒ 这三条合起来解释了 06 篇的结论：**AI 的"瞎话"不是因为它在编，是因为它被要求在没有数据的情况下做几何决策。**

## 2. 四类风险，按「会死人的程度」排序

自研的真实难点不在解析，在这四件上。排序依据是"出事后能不能挽回"。

### R1 · 几何计算的性能与正确性（工程主线）

`min_clearance` / `fits_where` / `loop_area` / `cross_split` / `shared_path` 每一条展开都是多边形运算 + 空间索引。

- naive 写法全板跑最小间距是 O(n²)，**一块 500 元件的板子会直接卡死**；
- 必须 shapely + rtree（或等价）+ 分层预计算；
- **关键划分：「加载时预算」vs「按需算」**——这个划分是整个系统的性能宪法，一旦定错后面全部返工。

处置：性能不是优化阶段的事，是**架构阶段的事**。Discrete 层装什么、Oracle 算什么的边界，实质就是这条划分。

### R2 · 写路径的静默失败（最危险的单点）

> **⚠ 已修正（实测）**：立创 V3 **不是** append-only 日志，也没有 `ticket` 取胜；
> 保存是原地重写一个成员（见 `13` 篇 §1）。"静默失败"这个风险判断仍然成立，
> 只是机制换了：字段数/单位写错、记录被应用忽略，文件照样打开、DRC 照样绿。

立创 V3 是 **append-only 日志 + 最终一致性**：改一个元件位置不是编辑那一行，是追加一行并以更大的 `ticket` 取胜。

- `ticket` 打小了 → 修改**静默消失**。文件看起来没坏、JSON 合法、IDE 打开后位置没变。
- 这类错误的特征与 03 篇判据同构：**错了之后 DRC 全绿**。

处置（项目级红线，不可协商）：

1. **写完必回读校验**：追加后重新按合并规则求当前状态，与意图逐字段比对；
2. 回读不一致 → **报错，不许沉默**；
3. 遵守「宁可报错不给错答案」——拿不到证据就返回错误或低置信标注，绝不猜。

### R3 · 双向保真度（生死线，不是质量指标）

写出去的东西用户要用真 EDA 打开。走线断、覆铜丢、封装位移——**信任一次就死**，后面再准也没人用。

这解释了 05 篇「apply 前必 checkpoint」的真正理由：不是流程优雅，是因为**写坏是不可逆损失**（KiCad 原理图改写无撤销栈；立创日志追加后语义依赖合并规则，错行留在日志里）。

处置：任何写操作前留快照；写后校验；失败可一键回滚到快照。

### R4 · 能力边界（必须提前说清，且**双栈不对称**）

| 能力 | 立创 EDA Pro | KiCad 9 / 10 |
|---|---|---|
| 原理图在线读写 | 有（`SCH_*`） | **无**——IPC 只覆盖 PCB 编辑器，原理图插件要 KiCad 11 |
| PCB 在线读写 | 有（`PCB_*`） | 有（IPC API） |
| 无 IDE 运行 | 需 IDE + 开「外部交互权限」 | headless 也要 KiCad 11 |
| 脚本层 | JS/TS 扩展 | SWIG 已弃用、KiCad 11 移除 |

⇒ **"双栈双域"这个目标在 KiCad 侧必然退化为：PCB 可在线，原理图只能改 S-expr。** 这不是我们的实现选择，是上游的能力上限。对外承诺必须按此口径，否则用户会问"为什么 KiCad 原理图不能撤销"，而我们无法回答。

## 3. 双栈不是两次开发：adapter 边界的三条硬约束

用户明确要求两端都支持。**但"都支持"不等于"两套实现"**，也不等于"两边同一时间做到同样的深度"。

真正的风险是：**先做一端、后补另一端 ⇒ 统一层被第一端的形态污染 ⇒ 适配第二端时返工。** 这三条约束就是为了把返工堵在架构阶段。

### C1 · 单位与坐标轴归一化**只允许发生在 adapter 边界**

- Canonical 内部**只允许 mm + Y 轴向上**，无例外；
- 立创内部是 **0.01 英寸 + Y 轴向下的**；KiCad 是 mm + Y 向上（内部 nm）；
- 转换责任 100% 在各自的 adapter 里，**Oracle 一行都不许出现单位换算或 Y 翻转**。

为什么必须在架构阶段定：这是典型的"画面看起来对、量出来差 25.4 倍或整体翻转"的错误，**DRC 全绿、肉眼也未必立刻发现**（尤其整板翻转后对称的板子看着一样）。后补意味着所有查询都要重测一遍。

### C2 · 一端缺失的事实**必须显式标缺失，不许用另一端的默认值填充**

同一事实在两端存放位置不同，且有的端根本没有：

| 事实 | 立创 | KiCad |
|---|---|---|
| 设计规则（线宽/间距） | `.epcb` 的 `RULE` 行（`ruleType:3` 线宽、`1` 间距矩阵） | **不在 `.kicad_pcb`**——在 `.kicad_pro` / `.kicad_dru` |
| netclass / 差分对 | 属性机制 | `.kicad_pro` |
| 焊盘电气类型 | 符号 `.esym` 的 `PIN` + `ATTR` | pad 的 `pintype` |
| 覆铜填充结果 | **单独文件** `.ecop` | 就在 `zone` 的 `filled_polygon` 里 |

⇒ Canonical 的对应字段必须带 `source` 与 `missing` 三态：`present` / `absent_in_format` / `not_loaded`。
**"读不到规则"和"这块板没有规则限制"是两个完全不同的事实，混为一谈就是给 AI 递错答案。**

### C3 · Oracle 只吃 Canonical，不认识任何一端格式

这条是 05 篇三件套分离的直接推论。判据很简单：**Oracle 代码里出现 `epcb` / `kicad` / `ticket` / `0.01` 这些字符串，就是架构破了。**

它的价值在于：新增第三端（Altium/AD、嘉立创其他工具）时，只加一个 adapter，Oracle 零改动。

## 4. 分期：环境决定了实现次序，但不能决定架构次序

### 4.1 现实约束

**当前机器只装了立创 EDA Pro，没有 KiCad。** 这个事实决定了：

- **能做真机验证的只有立创**——包括读写、实时交互、以及用户肉眼比对；
- **KiCad 侧可以开发和单测，但无法验收**：`.kicad_pcb` 是纯文本，解析和写文件都不需要装 KiCad，但"写完之后 KiCad 能不能正确打开"这件事**没有 KiCad 就验不了**，只能等装了再验。

⇒ 所以不是"放弃 KiCad"，而是 **KiCad 的写路径必须标记为`未验收`**，直到装上 KiCad。这一点要在代码和文档里都写死，不许拿"单测通过"冒充"能打开"。

### 4.2 立创先行反而是好事（原本我判断反了）

初稿认为 KiCad 格式更简单、能绕开 R2/R3/R4。但立创先行有两个**环境层面**的独特优势：

**① 立创自带 DRC 引擎，理论上可当免费的地面真值（ground truth）。**
如果扩展 API 能取到 DRC 结果，那么：

```
我们的 min_clearance 算出来的值  ←→  立创 DRC 报的违规  ←→  用户屏幕上的红标
```

三方可交叉校验。**这是 KiCad 侧给不了的**（KiCad DRC 要靠 `kicad-cli` 或 IPC，且没有 IDE 就没有可视反馈）。
⚠️ 待验证：扩展 API 是否暴露 DRC 结果读取。**这是第一步就要试的事**——能取到，校准成本降一个数量级；取不到，退回"用户肉眼看 IDE 红标"的人工校准。

**② 立创有实时 IDE，用户能当场看见我们算得对不对。**
这是最强的 fixture 机制：**任何几何量的错误都可以被肉眼立刻发现**，不必等打样。对比之下 KiCad 侧只有冷冰冰的文件。

### 4.3 分期定稿

| 期 | 范围 | 完成标志 | 风险覆盖 |
|---|---|---|---|
| **V0** | **双 adapter 都写、双 adapter 都读；Oracle 只跑只读查询** | 同一块板的等效内容，在两端解析出来的 Canonical 一致（用跨端 fixture 断言） | R1 全暴露；R2/R3 不触及 |
| **V0.5** | **立创真机只读**：接上 IDE，11 个查询返回真值；用立创 DRC 做校准 | 我们的最小间距 vs 立创 DRC 违规，逐条对得上 | R1 + 单位/轴向（C1）实锤 |
| **V1** | **立创写路径**（追加 + ticket + 回读校验 + 快照） | 写入后 IDE 内可见；回读不一致必报错 | R2 正面攻坚 |
| **V2** | **KiCad 写路径**（装 KiCad 后才做） | 写出的 `.kicad_pcb` 在 KiCad 里打开无异常 | R3 |
| **V3** | KIcad 原理图（S-expr，明确标注无在线/无撤销） | — | R4 边界对外说明 |

**为什么 V0 要双 adapter 一起：** 因为 C1/C2 只有"两端同时在场"才能被验证。只做一端时，单位、Y 轴、缺失事实三件事都看不出问题——**单端开发永远发现不了适配层设计错了**。这是本文最重要的排期理由。

### 4.4 立创侧的前置动作（需用户手动做一次）

- 装并启用官方扩展 **`run-api-gateway`**（Apache-2.0）；
- 在 IDE 里**开启「外部交互权限」**，否则 `SYS_WebSocket` 直接失败；
- 端口区间 **49620–49629**。

> 06 篇提到的现象要在这里重申：**很多"AI 不会用立创 MCP"的报告，真实原因是权限没开，不是模型不行。** 这会直接表现成"连不上"，容易误判成我们自己的 bug。

## 5. 验收判据：编制（fabrication）是可观测的，成功率不是

不能写"成功率变高"——成功率受运气影响，不可归因。

**V0 判据：模型是否在编造一个它没测过的距离。**

观测方法：看 tool 调用序列里有没有**凭空出现的坐标或距离**——即模型给出的几何量，在之前的调用返回里从未出现过。目标是把数量降到 0：模型每次做几何决策都必须先问 Oracle。

⇒ 一句话：**V0 成功 = 模型不再需要猜几何。**

## 7. 待议议题登记（下一轮）

用户 2026-10-27 明确指示：**先不动手，规划阶段；后续讨论「板框 / 开槽」，即板框层与机械层。**

以下几项在 01~06 篇里均**未充分展开**，需下一轮专门过：

1. **板框（Edge.Cuts）的表示**——是线的集合还是闭合区域？多闭合环（挖孔）怎么表达？板框自身的可通行性与机械限制怎么进占用图？
2. **开槽 / 槽孔（slot）**——立创 `PAD` 的 `holeData: [SLOT, w, h]` 是原生支持的；KiCad 侧用槽孔 pad 还是板框内环？两种表示在 Oracle 里是否需要统一成同一类几何对象？
3. **机械层（Mechanical）**——KiCad 有 `User.Drawings` / `User.Comments` / `Mechanical` 一族层；立创有机械层与 `ATTR`。**哪些属于"设计事实"，哪些只是"文档装饰"**——这条线划不出来，Discrete 层会装进大量垃圾。
4. **禁布区 `REGION` flags 与板框的关系**——立创 `flags` 编码（`2` 禁器件 / `5` 禁走线 / `6,8` 禁填充 / `7` 禁一切铜）与板框裁剪是两套机制，谁优先、如何叠加。
5. **机械约束是否进 Budget**——外壳高度限制、螺丝孔净空、板边元件退让，能不能像 04 篇的电学预算那样落成可机判约束。
6. **双栈在此处的差异**（新增）——KiCad 板框就是 `Edge.Cuts` 层上的图形，立创板框有独立概念且能带圆角/开槽信息。**同一块物理板在两端可能用不同几何表达，Canonical 必须选一种并声明另一端的转换损失。** 这是 C2（缺失显式标注）在板框上的具体化。

> 这些不只是"画板框"的实现问题，而是**"板子的边界几何算不算一类事实"**的建模问题。定不下来，Discrete 层就会在板框和机械层上先烂掉。

## 8. 当前不做的事

- 不写 `info_manifest.yaml`（虽是契约，但需先过 §7 的板框/机械层议题，否则契约要返工）
- 不实现 Oracle 的 11 个查询
- 不选 fixture 板
- 不 fork 任何仓库
- 不装 KiCad（等需要验 V2 时再说）

理由：§7 的结论会改动"哪些算事实、哪些算装饰"的基本划分，而那是契约的目录结构。**目录没定就写条目，等于先写代码后定接口。**
