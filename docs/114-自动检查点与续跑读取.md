## 2. 能改的是「接回来」的代价

压缩之后要补回记忆，代价是让模型重写一篇多页交接摘要（17:52 那次压缩请求本身 85 s）。上一版给了 `board_journal`，但它要求**人记得写**。这一版把它变成默认行为：

- 每次 `board_apply` **成功落盘**后自动追加一行 `kind="apply"`，约 80–120 B；
- `board_journal(action="resume")` 从最新的 `kind="apply"` 开始，带它之后的所有 note，**回包上限 4096 B**，超了从最旧一端丢；
- 没有 apply 条目时回 `no_checkpoint=true`，不把尾巴冒充检查点。

所以一次「断了」的重建路径从「重写一篇摘要」变成「一次 4 KiB 的读」。

## 3. 五条自检与它们的反向对照

| 自检 | 正向 | 反向（能失败的方向） |
|---|---|---|
| 自动落行 | 成功 apply 后 journal 多 1 条 | 回包 dict 用 `sort_keys` 全等比较，**改一个字节就 FAIL** |
| 不造假 | — | `dry_run` / `status=error` / 回包里没有文件 → 三条都必须写 0 条 |
| resume 起点 | 最新 apply + 之后两条 note，共 3 条 | 顺序必须正好是 `apply, note, note`；`reply_bytes ≤ budget_bytes` |
| 无检查点 | 只有 note 时 `no_checkpoint=true` | 若实现退化成「返回尾巴」就会 FAIL |
| 关掉时 | `auto()` 返回 `None` 不抛 | `resume` 必须 `status=disabled` 且 `entries=[]` |

## 4. 用法

```jsonc
// 断了以后，第一条调用
{"action": "resume"}                    // 4 KiB 以内：最后的落盘 + 之后的想法
{"action": "tail", "limit": 8}          // 只要尾巴
{"action": "add", "kind": "note", "text": "下一步 g4n6：SWDIO 东列 -> J2B.19"}
```

## 5. 仍然没解决

- 压缩 46 次 / 空回答 32 次这件事本身，MCP 管不了（宿主行为）。
- 压缩后 5.5 万 tokens 的地板，MCP 只能通过「每次回包更小」间接推迟它。工具表 `core` 档 46 个工具 / 54.9 KB、`all` 档 191 个工具 / 301 KB 仍未削；削它必须**先量出「削完断线率是否真下降」**，本轮没动。
- `board_journal` 只能记「我写了什么」，永远不能证明板子是好的 —— 每次 `resume` 都自带这句话。
