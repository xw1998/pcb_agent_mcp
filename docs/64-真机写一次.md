# 64 · 真机写一次：从「一次都没写过」到「写进去、落盘、重启还在」

> 这一篇补的是 0.0.60 之前一直挂着的一条：`lceda_live` 的**读**路径在 2026-10-28 就已经
> 打通过，但**写**一次都没跑过——所以 `lceda_pcb_write` 的每一份答案都硬编码
> `verified_against_app: false`。2026-11-01 在真机（LCEDA Pro **V4.1.60**，bridge
> **`4.1.60.198f38ab`**）上把 create / delete / move / save 各跑了一遍，并且把
> 「写进去了」这件事拆成四级证据：**探针动 → 文件变 → 关掉重开还在 → 整个应用重启还在**。
> 本篇只记读数与坑；判据如何进代码见 `lceda_write.VERIFIED_WRITES`。

---

## 1. 为什么不能「打开工程然后直接写」

第一版想当然的做法是 `lceda_pro_open(path=工程文件)` 之后写。实测：

| 调用 | 返回 |
|---|---|
| `available_endpoints()` | `['JLCEDAPro0c65189e']` |
| `ping()` | `{endpoint, bridgeVersion: '4.1.60.198f38ab', resultChannel: true}` |
| `eda.dmt_Project.getAllProjectsUuid()` | `[]` |
| `eda.dmt_Project.getCurrentProjectInfo()` | `null`（不是报错，就是 null） |
| `eda.dmt_Pcb.getAllPcbsInfo()` | `null` |

`lceda_pro_open` 建的是一个**后台渲染会话**，主窗口的 `eda` 全局看不到那个工程。
所以「open 完就写」不是签名写错，是**没有当前 PCB 文档**——`getAllPrimitiveId()`
会抛 `Cannot read properties of null (reading 'map')`，看着像调用错，其实是对象不存在。

真正能写的顺序（四步，一步都不能少）：

```js
const proj = await eda.dmt_Project.createProject('pcb_agent_mcp_write_probe', 'mcp-write-probe');
const P = '6a0fd106c55d01ef5849e445a8394f3d4e5636eeb95857346b8d879cf12a5903';
await eda.dmt_Project.openProject(P);            // true
const pcb = await eda.dmt_Pcb.createPcb();        // '0443ad92858f062a'
await eda.dmt_EditorControl.openDocument(pcb);    // '0443ad92858f062a@6a0fd106…a5903'  <- tabId
```

`openDocument` 返回的 `"<pcbUuid>@<projectUuid>"` 就是后面 `closeDocument(tabId)` 要的
tabId；只有它返回之后 `pcb_Document.getCanvasOrigin()` 才不是 `null`。

> **工程落在哪**：`D:\lcedapro\project\pcb_agent_mcp_write_probe.eprj2`（v4 格式）。
> 全程没有碰用户的 `OneDrive\Documents\LCEDA-Pro\`——那份只 copy 出 `.epro/.eprj` 到
> `_scratch/` 做只读比对，`sha256` 与源文件逐位相同。

## 2. 四级证据（第一轮）

### 2.1 探针动了

```
lceda_pcb_write(op='create',
  code  = "eda.pcb_PrimitiveLine.create('', 1, 0, 0, 10, 0, 0.2)",
  probe = "(await eda.pcb_PrimitiveLine.getAllPrimitiveId()).length")
```
`report: before=0, after=1, changed=true`，`ran.value = {ok:true, id:'62e0d3e03e906d83'}`，
`duration_ms 48`。签名 `create(net, layer, startX, startY, endX, endY, lineWidth?, primitiveLock?)`，
`layer 1 = Top Layer`——这两条都是 `doc.api` 从应用自己嘴里问出来的，不是猜的。

### 2.2 文件变了

`pcb_Document.save()` 之后，工程文件：

| 时刻 | 字节 | sha256 前 12 位 |
|---|---|---|
| save 之前 | 409600 | `a8872034…` |
| save 之后 | 569344 | `a14010a1…` |

### 2.3 关掉重开还在

`closeDocument(tabId)` → `true`；再 `openDocument(pcbUuid)`，行数仍 **1**，
`getAll()` 给出 `{id:'62e0d3e03e906d83', net:'', layer:1, sx:0, sy:0, ex:10, ey:0, w:0.2}`。

### 2.4 整个应用重启还在

`Stop-Process lceda-pro -Force` → 重新拉起 → 管道回来 → 按 uuid 从磁盘
`openProject(P)` = `true` → `getAllPcbsInfo()` 列出 PCB1/PCB2 → `openDocument` →
**`getAll()` 返回 `{layer:1, sx:1, sy:1, ex:21, ey:1, w:0.25}`**（几何逐位一致；
primitiveId 按预期变成新的 `1bca0d817bdc7b09`）。

同轮还跑了：`delete('62e0d3e03e906d83')` → `before=1, after=0`（再 save，sha 变
`22fd2d4a…`，size 仍 569344）；`create('', 1, 1, 1, 21, 1, 0.25)` + save → **585728 B**。

## 3. 第二轮：走工具层，而不是手写 client 调用

第一轮的读数证明的是「这条通路能用」，但它是用手写的 `client.invoke` 打出来的。
第二轮换成**工具自己**跑，把「生成器 → 写入 → 复读」整链验证一遍：

1. `lceda_write_snippet(op='create', class_name='PCB_PrimitiveLine',
   property='pcb_PrimitiveLine', argsv=["''",1,1,5,21,5,0.3])` →
   生成 `return await eda.pcb_PrimitiveLine.create('', 1, 1, 5, 21, 5, 0.3);`，
   并附 `probe: return await eda.pcb_PrimitiveLine.getAll();`（`evidence: exact_name`）。
2. `lceda_pcb_write(op='create', code=<上面那句>, probe='…getAllPrimitiveId()).length')`
   → `before=1, after=2, changed=true`，`verified_against_app: true`。
3. `op='save'` → `verified_against_app: true`，`verified_by` 明确写着
   「THIS call's save was not itself read back」。
4. `move`：`return await eda.pcb_PrimitiveLine.modify('1bca0d817bdc7b09', {startX: 2});`
   → 探针 `(getAll())[0].startX` `1 → 2`。`modify(primitiveId, property)` 的两参数
   形状同样是 `doc.api` 报的，不是我猜的。
5. **再一次**杀进程重启、按 uuid 重开，`getAll()` 返回两条：
   `(2,1)-(21,1) w 0.25` 与 `(1,5)-(21,5) w 0.3`。
   ——`startX` 从 1 变 2 这件事**跨两次重启都还在**，这不是内存里的假象。

### 3.1 负控制（这一轮同时做的、必须能失败的三条）

| 负控制 | 期望 | 实测 |
|---|---|---|
| `op='create'` 但 `code='return 1;'`（什么都没创建） | 拒绝，且不升格 | `WRITE_HAD_NO_EFFECT`，`verified_against_app: false` |
| 表外 op（当时 `move` 还没进表） | 探针确实动了也不放行 | `changed: true` 而 `verified_against_app: false` |
| 桥版本不匹配（`'9.9.9'` / 不传版本） | 一律 false，文案回到旧版 | false，`not_verified` 仍是旧的两条 |

第一条尤其重要：如果 `verified_against_app` 是「版本对上就 true」，那么一个**什么都没干**
的 create 也会被打上「已验证」，闸门就成了装饰。

## 4. 量出来的坑（都能咬人）

1. **会话收到的是函数体，不是表达式。** `invoke(code='1+1')` 返回 `null`；
   `invoke(code='return 1+1')` 返回 `2`。所以探针也必须写 `return`，
   而那正是 `lceda_write_snippet` 生成出来的形状（它自己带 `return`）。
2. **空字符串要写成 `"''"`。** `argsv` 里的字符串是**原样插入的 JavaScript**，
   空串会被当成「空代码」拒掉（`argument 1 is an empty string`）；要传空 net 就传两个单引号。
3. **`SNIPPET_NO_RECEIVER` 不是 bug。** 应用给的 `callPath` 是 `pcb_PrimitiveLine.`，
   而生成器要求 `eda.<prop>.`——类名不是属性名，它**不会**替你小写化，必须显式
   `property='pcb_PrimitiveLine'`。
4. **`save()` 是「返回了」，不是「写完了」。** 一次 save 之后 0.1 s 读磁盘还是旧字节，
   下一次检查（约 8 s 后）读到新字节（585728 → 905216，sha `0651d449…`）；
   另一次 save 在 0.5 s 内就改变了 sha 而 size 不变。**所以判「落没落盘」必须轮询，
   不能 stat 一次就下结论**——这条差点让我把「异步落盘」误判成「save 没落盘」。
5. **重开后的 `session.list` 可能是空的。** 应用重启后要先 `open`（或触发一次文档打开）
   才有会话；再之后 `getCurrentProjectInfo()` 有一次 60 s 超时，而
   `getAllPcbsInfo()` 在同一个会话里正常返回——**单个调用超时不等于会话死了**。
6. **`JSON.stringify` 不能用来判空。** 空数组 stringify 回来是 `'{}'`（桥的序列化把它
   当对象收了）；要判空就直接要那个数组，别绕字符串。
7. **Electron 窗口不向 UIA 暴露控件。** 早期想点掉一个模态框，UIA 枚举 `BUTTONS 0`，
   `SendKeys {ENTER}` 与 `SetCursorPos+mouse_event` 打了 7 次都没反应；最后靠重启应用。
   ——所以这条路只能走应用自己的 command space，不能靠模拟点击。

## 5. 这次**没有**证明的东西（必须单独列）

- **探针读到的 ≠ 屏幕上看到的。** 上面每一条读数都是应用自己的返回值，没有人对着屏幕确认过。
- **参数写错会不会被静默接受。** 一个「什么都没干」的 create 会被探针抓到，
  但一个「干了别的事」的 create 抓不到（计数照样 +1）。
- **`.epro` 归档写路径。** 本篇验的是**活编辑器**路径；0.0.5x 那套「写 `.epro` 字节」
  的归档路径，写出后能否被应用重新打开，仍然是 `not_verified`。两者不许互相顶替。
- **厂商 `--mcp` 传输。** 这个构建的 exe 在 app 看到 argv 之前就把 `--` 参数拒了。

## 6. 落进代码的是什么

`lceda_write.VERIFIED_WRITES` 里只有一条：`4.1.60.198f38ab` → `ops: [create, delete,
move, save]`，附 `measured_on`、逐条读数与 `still_not_verified`。`run(...)` 只有在
**三个条件同时成立**时才把 `verified_against_app` 打开：调用方说了桥版本、版本在表里、
这次的 `op` 在那条记录的 `ops` 里且**这一次**效应被读到（change 类必须探针动）。

因此：

- 没传 `bridge_version`（旧调用方式）→ 答案与改动前**逐字相同**；
- 未列出的桥版本 → `false`；
- `write`（调用方自定义那段代码）永远不进表 → 永远是 `false`；
- **默认行为不变**：既有 45 条 `test_lceda_live` 用例除描述文案外不需要改。

这是本项目第一次把 `verified_against_app` 从 `false` 翻成 `true`，属于**显式的输出变化**，
已在 `CHANGELOG.md` 的 0.0.61 节单独登记，并在 `README.md` 的能力栏写明「只覆盖这一条桥版本」。
