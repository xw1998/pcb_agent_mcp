# 10 · 桌面控制层与双栈读路径

> 回答的问题：**"AI 要不要知道 EDA 开着没、哪个工程在跑？知道了能干什么？"** 以及
> **"两份完全不同的二进制格式，凭什么能喂给同一个度量层？"**
>
> 本文记录 0.2.0 落地时的口径与取证，包括三处"数字齐全但答错了"的缺陷。

## 1. 为什么 MCP 需要一个桌面控制层

模型的全部输入是文本。它看不见任务栏，也点不动"文件 → 打开"。于是有两类问题它只能靠猜：

| 问题 | 靠猜的代价 |
|---|---|
| "立创装在哪？" | 猜路径 → 启动失败 → 模型改写一个"也许能用"的路径 |
| "工程打开了吗？" | 猜"启动了进程就是打开了" → 后续所有操作对着空窗口说 |
| "这个 DRC 是我这次的板子吗？" | 猜 → 对着**上一次**的板子给结论 |

`mdk_agent` 在 Keil 上撞过的坑正是第三种：一个残留实例继续应答，答案来自早就不是屏幕上那块板子。
所以本层的第一原则不是"能启动"，而是**每个回答都必须有来源，且能说清来源强弱**。

### 1.1 证据强度（这是本层的核心设计）

`detect()` 按证据强弱排序，并把用到的证据写进 `source`：

| 顺序 | 来源 | 强度 |
|---|---|---|
| 1 | 显式路径（用户给的） | 最强，但可能过期 |
| 2 | **运行中进程的镜像路径** | 最强的事实证据：进程就在那儿 |
| 3 | 盘符扫描（遍历 A..Z，支持 `{ver}` 通配） | 中等：装过就算 |
| 4 | 注册表 `Uninstall` 键的 `InstallLocation`（32/64 位双视图） | 中等偏弱：卸载残留会骗人 |

找不到也回带 `tried` 列表 —— "我找过这些地方"和"我没找"是两件事。

`status()` 的 `projects_open` 只来自**窗口标题**。标题里没有工程名就是空列表，
不是"大概是这个"。这条在 `open_project()` 里变成三态：

```
opened = "confirmed"    窗口标题里出现了文件 stem
         "unconfirmed"  进程起来了，但没有任何窗口标题含该 stem
                        （附 instances_after，并说明"启动进程 ≠ 打开工程"）
```

立创 Pro 的命令行开工程形式 `lceda-pro.exe <工程.epro>` **没有在真机确认过**，
所以返回里固定带 `open_argv_verified: false`。KiCad 的形式是确认过的，为 `true`。

到这一轮为止，这条从"没试过"变成了"试过、并且知道它为什么不成立"（实测，用
`_scratch/argv_probe/` 里的一份临时副本，绝不碰用户工程目录）：

| 启动方式 | 结果 |
|---|---|
| `lceda-pro.exe <工程.epro>` | **0.5 s 后 rc=1 退出**，无窗口，`%APPDATA%\JLCEDA Pro` 无写入 |
| `lceda-pro.exe`（无参数，cwd=安装目录） | **0.5 s 后 rc=0 退出**，同样无窗口 |
| `cmd /c start "" lceda-pro.exe` | 同上，没有进程留下 |
| 对照：`kicad.exe` | 正常起来（标题 `KiCad 10.0`）并可被 `close()` 关掉 |

所以"启动进程"这一步对立创**在当前环境下都不成立**，更不能声称打开了工程。
`open_argv_verified` 保持 `false`，`opened` 只会是 `unconfirmed`；桌面控制对立创侧
目前可信的部分只有"装在哪"（4.1.60，盘符扫描命中）与"在不在跑"（进程 + 窗口枚举）。

### 1.2 关闭 = 点 X，不是杀进程

`close()` 对每个可见窗口 `PostMessage(WM_CLOSE)`，然后轮询等它自己退。
只有调用方显式 `force=true` 才 `TerminateProcess`。

理由不是"温柔"，而是**未保存的改动**：EDA 收到 WM_CLOSE 会弹保存框，用户自己决定。
静默杀进程等于替用户丢工作。若进程在超时后仍在，返回里会指向"可能有模态框/未保存"。

### 1.3 一条硬边界：**永不触碰工程文件**

用户的原话是"不许瞎删我工程"。落成三条可执行的约束：

1. 本层只做三件事：读进程/窗口/端口状态、启动进程、发关闭消息。**不打开工程文件读写**。
2. `open_project()` 的路径不存在时返回 `PROJECT_NOT_FOUND`，消息里写死
   "this tool never creates files"。
3. 测试固化：`tests/test_tools.py` 对每个 board 工具调用前后比对 **sha256 与 mtime**，
   `tests/test_kicad_pcb.py` / `tests/test_epro.py` 各自再比一次。

端口归属用 `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_LISTENER)` 查，**不用 netstat**：
外部命令慢、本地化输出、沙箱里可能没有。探活先查监听表，查不到再 connect
（`mdk_agent` 实测纯 connect 探活 60 次有 18 次 timeout 误判）。

## 2. 双栈读路径：两份格式，一个模型

立创 `.epro` 与 KiCad `.kicad_pcb` 的差异不在"语法"，在三处**会静默出错**的语义：

| 陷阱 | 立创 Pro | KiCad | 不处理的后果 |
|---|---|---|---|
| 单位 | ~~整数 `0.01 inch`（0.254 mm）~~ → **mil**（实测；标签只是显示单位） | mm | 每个尺寸小 25.4 倍，而 DRC 全绿 |
| Y 轴 | 向下 | 向下 | 模型里一个朝上一个朝下，元件位置全反 |
| 网络标识 | 对象 id | 整数 code | 同一条网络两个名字，按网络比对的度量全空 |

对策是把归一化**只做在 adapter 边界一次**（`docs/07` §3 的 C1），Canonical 内部只有
「mm + Y 向上 + 网络用名字」。

### 2.1 网络名归一化是踩出来的

第一版把 KiCad 的 `net` 原样塞进 `tracks[].net`（整数 code `2`），而 pad 上塞的是名字 `"VCC"`。
结果 `board_clearance(net_a="VCC")` 回 `NO_GEOMETRY`，`board_loop_area("VCC")` 回"这条网络没有走线"——
**数字一个不缺，答案全错**。

修法是 `Board.resolve_nets()`：adapter 结束时，把 tracks/vias/zones/pads 的 `net` 一次性
解析成名字，且 `net_name()` 同时接受 `2` 与 `"2"`（KiCad 的 nets 字典键是 int）。

> 可复用判断：**同一个量出现两套写法，就是两套起点**。凡是跨模块传递的标识符，
> 必须在唯一的边界处归一，并在下游只认一种形态。

### 2.2 `.epro` 是 append-only 日志，不是快照

> **⚠ 已修正（实测）**：本节整段是当时的猜测，**实测不成立**。
> 真实 `.epro` 的记录流是**普通快照**：一个 tag 一行、id 唯一、没有 ticket 取胜回放；
> 坐标是 **mil**（不是 0.01 英寸整数）；一次保存是**原地重写一个成员**，
> 不是追加。证据与全部真实布局见 `13-立创实测-真实存储与记录格式.md`。
> 下文保留原文，作为"猜测长什么样"的记录。

一行 = `{"type","id","ticket"}||{payload}`。同一个对象会出现很多次，**ticket 最大的才是它现在的样子**；
payload 全空 = 删除；还有 `DELETE_DOC` 整篇删除。

天真的读法（取第一条 / 取最后一条）拿到的是一块**曾经存在过的板子**。所以 `read_document()`
按 `(type,id)` 取最大 ticket，并把统计写进 `source.log_stats`
（`superseded` / `deleted` / `unparsable`）—— 静默丢掉无法解析的行，正是"读出一块从未存在过的板"的起点。

### 2.3 字段名未公开 ⇒ 声明，不猜

`.epcb` 的 payload key 名没有公开 schema。本 adapter 走候选表 `CANDIDATES`（如 `x` ← `x/left/px/startx`），
未命中的字段收进 `unmapped` 并逐条 `declare_absent`，**绝不填 0**。
配套的 `epro_inspect` 专门用来"关掉"未知字段：它列出成员、每种类型的对象数、
以及每种类型前几条 payload 的**原始 key 名**。拿到真实工程后的正确动作是先 inspect，再补候选表。

### 2.4 缺失的事实必须被声明（C2）

Canonical 用两张表记账：`present[fact] = {present: bool, note?}` 与 `absent = [{fact, reason}]`。
`FACT_KEYS` 是闭合集，写错键名直接 `ValueError`（防止"记了一笔账但没人认识这个科目"）。

这条不是洁癖，它直接决定下游能不能回答问题：

- 板上没有平面 zone → `cross_split` 返回 `FACT_ABSENT_IN_FORMAT`。
  回流路径的连续性**看不见**，"没发现跨分割"会让一块坏叠层在 DRC 里继续绿。
- 文件里没有叠层 → `loop_area` 返回 `FACT_ABSENT_IN_FORMAT`。
  猜一个介质高度 = 猜一个 EMC 答案。
- 只有一个 zone 轮廓、没有填充结果 → `pour_connectivity` 标 `polygon_source: outline_only`。

## 3. Adapter 的两个实现要点

### 3.1 KiCad：把 `Edge.Cuts` 还原成闭合轮廓

`gr_line/gr_arc/gr_rect/gr_circle/gr_poly/gr_curve` 混着用，线段还是无序的。
`_chain_segments()` 按端点容差 1e-6 串成环；bezier 折成 16 段；三点 `gr_arc` 求圆心定角度。
多条轮廓时**面积最大者为外框**，其余为开槽 —— 这条约定只对单板成立，拼板会有歧义，已记进精度声明。

footprint 上的 pad 是**相对坐标**，必须按 footprint 的旋转角变换到板坐标（再翻 Y）。
不做的后果是旋转过的元件所有 pad 都压在元件原点上，clearance 会报一堆假违例。

### 3.2 顺序与"最小可信"取舍

- `.kicad_dru`（条件规则）只取原文、不做解释，并声明"无可机判 schema"——它是一门小语言，硬解就是猜。
- `.epro` 的 `.ecop`（铺铜填充结果）暂不读，`zone_fill` 标为部分事实。
- 3D 模型（`.eblob` / kicad `model`）只记"有没有"，不解析几何。

## 4. Oracle 的口径（三处返工）

### 4.1 `clearance`：中心距减半宽，且必须真的比到

轨对轨用「中心线距离 − (w1+w2)/2」，**保守**（转角处会过报），精度声明里写明。

返工一：空间桶按 bbox 分格且不膨胀。两个相距 0.7 mm 的 pad 恰好落在不相邻的两个格子里，
**从来没被比较过**，`min_gap_mm` 返回 `null` —— 看起来"间距很大"，实际是"没算"。
修法：分格时按 `cell` 膨胀，并在 `precision` 里声明"`min_gap_mm` 只在小于该窗口时精确"。

返工二：指定了不存在的网络时返回 `ok` + 空结果。改成 `NO_GEOMETRY`，并列出实际有铜的网络名。

### 4.2 `loop_area`：直走线的 bbox 面积是 0

第一版用「走线 bbox 面积 × 到下层铜的距离」。一条直的 30 mm 走线 bbox 高度为 0，
于是**环路面积算成 0 mm²**，`status` 还是 `ok`。

正确的物理量是「走线长度 × 到参考平面的高度」（回流沿走线正下方返回）。
改为逐段累加长度，bbox 面积单列 `bbox_spread_area_mm2` 仅作参考。

> 这类缺陷的共同形态：**退化几何让公式安静地返回 0**。凡是"面积/长度/比值"类度量，
> 都要有一条退化用例（单点、直线、共线、零厚）在测试里。

### 4.3 `free_space`：回答"能放哪"，不是"多密"

占用栅格 + 余量 → 行游程 + 垂直生长取最大矩形。`free_ratio` 只是副产品，
模型真正要的是「坐标 + 尺寸 + 面积」的矩形列表。> 400k 格直接 `GRID_TOO_FINE`。

## 5. 差分阻抗为什么要单独成模块

单端闭式解**根本不能**回答 USB 90Ω / 以太网 100Ω：耦合会显著拉低阻抗，而单端公式里没有间距这一项。

```
微带   Zdiff = 2·Z0·(1 − 0.48·exp(−0.96·s/h))
带状线 Zdiff = 2·Z0·(1 − 0.347·exp(−2.9·s/b)),  b = 2h
```

`s/h ∈ 0.1..3.0`，越界只标 `validity_note` 不拒绝（趋势仍可用）。这条闭式的精度不是「±15% 以内」这种许愿式声明——它在本服务自己的二维场解上实测**偏低 8~11%**、方向一致（见 [docs/15](15-对账-推导对着厂商判决.md)），所以精度文案写的就是这句实测结论，并指向 `diff_impedance_field`。

反解时发现一处真缺陷：宽度搜索上界写成 `min(3h, 0.9h)`（等于 0.9h），
于是 `100Ω / 0.2 mm 介质 / 0.2 mm 间距` 被判 `UNREACHABLE`（可达带 112.9..208.5Ω）——
而这正是最常见的以太网目标。改为单端模型的 `w/h ≤ 3.0` 后解得 **0.234 mm**，
回代 `zdiff_recomputed = 100.0`。
