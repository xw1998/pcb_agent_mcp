# 24 · 立创 Pro 的进程内桥（它自己的命令空间管道）

这一页记的是**唯一一条能看见用户正开着的设计的通路**：立创专业版自己开在
`\\.\pipe\JLCEDAPro<8 hex>` 上的命令空间。它不是文件格式、不是 websocket 网关、
也不是我们自己实现的一套 API——是把一段 JS 送进编辑器进程里执行，再把应用自己的答复原样带回来。

实测环境：Windows，LCEDA Pro **4.1.60.198f38ab**，`D:\LCEDApro\lceda-pro\`，
日期 2026-10-28。模块 `src/pcb_agent_mcp/lceda_live.py`，工具 `lceda_pro_*`（6 个）。

## 24.1 先解决"它起不来"

前两轮记的"lceda-pro.exe 0.5 s 退出、死在 Electron 之前"是**错的**（见
[`10-桌面控制与双栈读路径.md`](10-桌面控制与双栈读路径.md) §1.1.3）。同一个 exe：

| 启动方式 | 结果 |
|---|---|
| bash 里直接执行（继承控制台） | rc 0，约 0.5 s 退出，零日志，无管道 |
| `explorer.exe "<exe>"`（等价双击） | 三个进程稳定（203 / 36 / 289 MB），管道数秒内出现 |

所以桥的第一个前提不是"写代码"，是"按用户双击的那条路启动"。这一条也解释了为什么
厂商自带的 `--mcp stdio|http` 服务器起不来：`--` 开头的选项被 exe 里 node 自带的
选项解析器以 rc 9 拒掉（`bad option: --mcp`），跟立创的启动器无关。

## 24.2 端点：名字能推导，但这台机器上算不出来

厂商代码里的推导是 `appName.replace(/\s/g,"") + sha256(userData).hex().slice(0,8)`。
按它算：本机活端点是 `JLCEDAPro0c65189e`，可 `0c65189e` 用 7 类候选 userData 路径
（`OneDrive\Documents\LCEDA-Pro`、`Roaming\LCEDA`、`Roaming\JLCEDA Pro`、
`Local\LCEDA-Pro`、`D:\lcedapro` 等）× 大小写 / 斜杠 / 后缀变体**一个都对不上**。

结论不是"公式错"，是"我们不知道它到底哈希了哪条串"。因此：

* `endpoint_name()` 保留（记录推导事实），但注释里写死"**不要用它去猜活端点**"；
* `connect()` 走**枚举 `\\.\pipe\` → 逐个 ping**，只接受**答复里带 bridgeVersion**的那个。
  名字对不算数——任何进程都能建一个同名的管道。

## 24.3 帧格式

一行一个 JSON，UTF-8，`\n` 结尾：

```
请求  {"id": 1, "op": "invoke", "timeoutMs": 60000, "session": "...", "code": "..."}
回复  {"id": 1, "ok": true, "value": ..., "logs": [...], "durationMs": 3}
失败  {"id": 1, "ok": false, "error": {"code": "EXECUTION_ERROR", "message": "boom"}}
```

限额（实测/常量）：请求 ≤ **4 MiB**，回复 ≤ **16 MiB**，默认预算 **60 s**。
`PipeTransport` 不设缓冲的读循环是 0.02 s 轮询 + 按 `\n` 切帧，超时就把管道关掉
（不关会让下一条请求读到上一条的残帧）。

## 24.6 两个会静默写错的坑

1. **文档名 ≠ 运行时属性名。** `doc.api` 说类叫 `PCB_Document`，代码里必须写
   `eda.pcb_Document`。这张映射表应用自己会随 `doc.api` 一起给
   （`callConventions.classToProperty`），所以**读它，不要背**。
2. **树类没有 `list()`。** `eda.dmt_Pcb.list()` 抛 `EXECUTION_ERROR`；正确的是
   `getAllPcbsInfo()` / `getPcbInfo()` / `getCurrentPcbInfo()`。另外
   `eda.pcb_Document.getCanvasOrigin()` 在没有 PCB 文档是"当前文档"时**回 null**
   ——那不是调用写错了，是前提没满足；别把 null 读成 0。

## 24.7 `invoke` 的代码跑在哪

`code` 是**一个 async 函数的函数体**，在编辑器的 render 进程里执行：

```js
// code 里可以直接写 return
const pcbs = await eda.dmt_Pcb.getAllPcbsInfo();
return pcbs.map(p => p.name);
```

* 作用域里有厂商的 `eda` 对象（`doc.api` 描述的就是它）；
* 传参走 `__CLI__.args`（本模块对应 `invoke(..., args=...)`）；
* 返回值必须可序列化（否则 `RESULT_NOT_SERIALIZABLE`），`console.log` 进 `logs`。

## 24.8 工具表（`lceda_pro_*`）

| 工具 | 干什么 | 证据 |
|---|---|---|
| `lceda_pro_status` | 枚举 + ping，报端点与 bridgeVersion | 真机 |
| `lceda_pro_api` | 问命名空间/类/方法的清单（含 `classToProperty`） | 真机 |
| `lceda_pro_open` | 在**运行中的**应用里开工程，回 sessionId；开之前和开之后各 ping 一次 | 真机（849 ms） |
| `lceda_pro_verify` | 一次给三个事实：管道答不答、有无存活会话、**工程是否真的加载**（`connected` 只等于第三条）；见 24.12 | 真机（`loaded=false` 的失败路径已实测） |
| `lceda_pro_recover` | 报管道状态（healthy / bridge_dead / not_running）；`confirm=true` 才真的重启应用；已有窗口时回 `ALREADY_RUNNING` | 状态机已测，重启未在本机复现 |
| `lceda_pro_sessions` | 列会话 | 真机 |
| `lceda_pro_close` | 关会话（可 destroy） | 真机 |
| `lceda_pro_run` | 在进程内跑一段 JS | 真机（只读片段） |

共同口径：`verified_against_app = true`（这些都真跑过），`endpoint` 与
`bridge_version` 一并回；`value` 是应用自己的答复**原样**，不加字段、不四舍五入。

错误码分两类，都带在新信封的 `reason_code` 里：

| 我们的码 | 何时 |
|---|---|
| `APP_NOT_RUNNING` | 没有管道，或所有候选管道 ping 都不应 |
| `APP_DIED_DURING_OPEN` | `open` 回了 sessionId，但紧接着的 ping 不应（应用没了应答能力；见 24.11） |
| `OPEN_NOT_CONFIRMED` | `open` 回了 sessionId、ping 也应，但 `getCurrentProjectInfo()` 是空对象（见 24.12） |
| `NO_PROJECT_LOADED` | `lceda_pro_verify`：管道健康但没工程（多半是窗口上有模态框） |
| `NOT_CONNECTED` | `lceda_pro_verify`：管道本身不健康 |
| `ALREADY_RUNNING` | 已有一个带窗口的实例，拒绝再起第二个（`lceda_pro_recover` / `desktop.launch`） |
| `RECOVER_NOT_CONFIRMED` | `lceda_pro_recover` 只报告不动作（默认行为） |
| `RECOVER_TIMEOUT` | `confirm=true` 后等在预算内没等到能应答的管道 |
| `APP_UNREACHABLE` | 管道打开/读写失败（应用多半退了） |
| `APP_TIMEOUT` | 帧发出去了但没在预算内回 |
| `APP_ERROR` | 应用报错但给的不是它公开的码（原码留在 `extra.app_code`） |
| `FRAME_TOO_LARGE` / `RESULT_TOO_LARGE` | 超 4 MiB / 16 MiB |
| `ARG_REQUIRED` / `ARG_INVALID` | 参数空 / 路径不存在 |
| 厂商码**原样透传** | `UNKNOWN_OP / INVALID_ARGS / EXECUTION_ERROR / SYNTAX_ERROR / TIMEOUT / SESSION_* / FUNCTION_NOT_FOUND / EXTENSION_NOT_FOUND / RESULT_* / FRAME_TOO_LARGE / PROTOCOL_ERROR / HELP_QUERY_FAILED / DOC_QUERY_FAILED / DOC_CLI_NOT_FOUND / INTERNAL` |

"应用没给码"时**不会**冒用 `INTERNAL`（那是厂商的词）：一律 `APP_ERROR` + `app_code: null`。

## 24.9 没验证的部分（逐条，别读成"差不多能用"）

1. **任何写**。没有 save、没有 create、没有 move、没有 delete。`lceda_pro_run` 的每次
   答复都写明"片段自己能写，本工具不替它担保"；写路径到底能不能被应用接受、写出的文件
   是否与编辑器自己保存的一致，**未知**。
2. **`open` 是否碰工程字节**。前后没做逐字节比对（只做了"文件存在"与"打开成功"），
   所以"open 不改工程"是**未证**，重要场合请先备份。
3. **`destroy` 的语义**。关会话时 `destroy=true` 只观察到 `status: closed` 且条目仍在
   列表里；是否会丢弃未保存改动没有实测（按"会丢"处理）。
4. **厂商 `--mcp` 传输**。`app.js` 里那套 CLI→MCP 运行时（`stdio`/`http`、
   127.0.0.1:3030、`2025-06-18`、`<prefix>.help/.discover/.call`）读得出来，但这个 exe
   在应用看到 argv 之前就把它拒了，所以**从未启动过**。
5. **`stop` / `doc.external` / `doc.format`**。会关掉用户应用或没有实测价值，未跑。
6. **多实例**。本机只有一条管道；同名前缀多实例时"取第一个能 ping 的"是否够用，未测。

## 24.11 「未找到 Bridge 服务，3 秒后重试」

现场状态：编辑器窗口还在，管道 `\\.\pipe\JLCEDAPro<8 hex>` 也还在，但**没有任何进程应答
ping**；窗口反复弹「未找到 Bridge 服务，3 秒后重试」，这个应用**不会自己重建管道**。

实测到过的一次触发路径：对一个 32 MB 工程做 `headless=true` 的 `open`，答复之后编辑器
的渲染进程就没了（进程列表空、弹上述对话框）。**机制不知道**，所以这里不声称修好了根因，
只做三件可核的事：

1. **不再默认 headless**。`lceda_pro_open` 的 `headless` 默认改为 `false`；headless 依然
   可用，但文档与答复里写明它是那条被观察到的触发路径。
2. **前后各一次 ping**（canary）。开之前 ping，避免把请求发给一个半死的应用；开之后 ping，
   失败就抛 `APP_DIED_DURING_OPEN`，把路径、大小、headless、耗时、应用自己的答复
   （`open_reply`）与前后 bridge 版本一起带出——**绝不把一个已经没人应答的 sessionId
   当成可用的返回**。成功时同样记录在 `open_trace` 里。
3. **`lceda_pro_recover`**：一次读清状态，三种结论
   `healthy / bridge_dead / not_running`。`bridge_dead` 就是要重启动，而重启 = 新进程，
   旧进程里没存的改动会丢，所以默认只报告；`confirm=true` 才 `force` 关掉再拉起来，
   并等管道重新应答（干净启动约 1 s 出管道）。

判据（都能反向失败）：没有管道 → `not_running`；有管道但 ping 不应 → `bridge_dead`；
ping 应 → `healthy` 且 `bridge_version` 非空。三条都在 `tests/test_lceda_live.py`
里用假 transport 覆盖，不依赖真机。
## 24.12 管道应答 ≠ 工程已加载

### 现场

`open` 回了一个 sessionId，`ping` 前后都答 `4.1.60.198f38ab`，`session.list` 里
`status: "alive"` —— 看着全绿。但：

```js
eda.dmt_Project.getCurrentProjectInfo()   // {}
eda.dmt_Pcb.getAllPcbsInfo()              // {}
```

工程**根本没加载**。窗口停在一个模态框上：

> 当前工程为V3以下版本，打开后将不再支持V2.2及以下版本客户端打开。……是否确认打开该工程？

触发它的是对 `_lceda/base.eprj`（从 `example-projects/示例工程_快速入门.eprj` 复制来的
**V3 以下**工程）做 `open`。所以：

- 「上一轮没连上」的判据错误在**只看管道**。管道活着只证明注入的命令空间在，不证明有工程。
- 用户看到的那个对话框是**版本升级确认框**，不是 24.11 的「未找到 Bridge 服务」。
  两者是不同的失败，不要混说。

### `eda.dmt_*` 的读接口是异步的，`await` 不能省

`invoke` 把片段当 **async 函数体**执行，所以 `await` 合法。这一条是判据能否成立的前提：

```js
eda.dmt_Project.getCurrentProjectInfo()            // [object Promise]
Object.keys(eda.dmt_Project.getCurrentProjectInfo()) // []  ← 永远是空，看着像"没工程"
await eda.dmt_Project.getCurrentProjectInfo()       // 有工程时才是对象
```

第一版 `PROBE_JS` 没写 `await`，于是 `loaded` 恒为 `false` —— 这正是本节要消灭的假绿
的镜像（假红）。**判据两侧都可能骗人，所以要能在真机上拿到一次 `loaded: true` 才算完**。

逐个实测（会话 `6cd67aab…`，工程未加载时）：

| 片段 | 结果 |
|---|---|
| `return await eda.dmt_Project.getCurrentProjectInfo()` | **永不返回**（promise 不 resolve，12.75 s 超时） |
| `return await eda.dmt_Project.getAllProjectsUuid()` | `[]` —— **工作区里一个工程都没有** |
| `return await eda.dmt_Workspace.getCurrentWorkspaceInfo()` | `{itemType:'Workspace', uuid:'Personal', name:'Personal'}` |
| `return await eda.dmt_Pcb.getAllPcbsInfo()` | `null` |

所以 `lceda_pro_verify` 现在的 `why` 分两句：工作区 0 个工程 ≠ 弹窗挡着。

### 一个不 resolve 的 getter 不该把其余读数带走

`getCurrentProjectInfo()` 没工程时**既不 resolve 也不 reject**，所以合并探针会整体超时。
`project_state` 因此加了降级探针（`CHEAP_PROBE_JS`：只问 `getAllProjectsUuid` 与
`getCurrentWorkspaceInfo`——这两个永远答得回来），超时时仍报：

```
loaded: false, project_count: 0,
probe_error: "APP_ERROR",
why: "the project getter never answered (…) and the client's workspace lists 0
      projects - there is nothing to load"
```

并且 `why` 按 `project_count` 分两句：0 → 没东西可加载；>0 → 渲染被挡住（多半是模态框）。
「不 resolve」本身就是读数，不是测不出来。

### 所以「没连上」的真实原因是两条，不是一条

1. **工作区里没有工程**（`getAllProjectsUuid()` = `[]`）。`open` 一个文件路径是"导入"，
   而导入要弹框/要时间；客户端从来没被导入过任何工程。
2. **那个 V3 升级框**是我上一轮 `open` 一个 SQLite 容器（`_lceda/base.eprj`）触发的，
   它在客户端自己的页面里，桥内 `document` 不存在 ⇒ **点不到**，只能人点。

容器是能离线判的（`project_container()`，读文件头，不信扩展名）：

| 文件头 | 容器 | 后果 |
|---|---|---|
| `SQLite format 3\x00` | 旧 `.eprj` | 4.1.60 必定弹「当前工程为V3以下版本…」 |
| `PK\x03\x04` | `.epro2` / `.epro` | 不弹该框 |
| 其它 | unknown | 不下结论 |

`lceda_pro_open` 默认 `allow_upgrade=false`：旧容器**在联系应用之前**就回
`PROJECT_NEEDS_UPGRADE`（带容器判定与 `next`），不再制造一个"回 sessionId 但其实没加载"的局面。

### 在桥里能做什么、不能做什么

| 事实 | 实测 |
|---|---|
| 命名空间必须带前缀 | `dmt_Project` 是 `undefined`，`eda.dmt_Project` 才是对象 |
| 可用命名空间 | `dmt_Board / EditorControl / Event / Folder / Panel / Pcb / Project / Schematic / SelectControl / Team / Workspace` |
| 未加载时的返回值 | **空对象 `{}`，不是报错** —— 这是最容易读成成功的地方 |
| 桥会话里有没有 `document` | **没有**（`Object.keys(window)` 抛异常）⇒ 模态框**点不到**，只能人在窗口里点 |
| `dmt_Schematic.getAllSchematicInfo` | 存在但**不是函数**；`dmt_Pcb.getAllPcbsInfo` 是 |
| 探针开销 | 2–4 ms，`logs: []` |

### 判据（三条，分开报，不合并）

```js
var o={loaded:false};
try{var p=eda.dmt_Project.getCurrentProjectInfo()||{};
    o.project=p;o.loaded=Object.keys(p).length>0;}catch(e){o.error=String(e&&e.message||e);}
try{var b=eda.dmt_Pcb.getAllPcbsInfo()||{};o.pcbCount=Object.keys(b).length;}catch(e){}
try{var s=eda.dmt_Schematic.getAllSchematicInfo()||{};o.schCount=Object.keys(s).length;}catch(e){}
return o;
```

1. 管道答不答 ping → `healthy / bridge_dead / not_running`（24.11）
2. 有没有 `status == "alive"` 的会话
3. **`Object.keys(getCurrentProjectInfo()).length > 0`** ← 只有这条意味着"下一次工具调用会落在工程上"

### 落地的四处

| 位置 | 行为 |
|---|---|
| `lceda_live.PROBE_JS` / `Client.project_state()` | 上面那段；无 session 时取最后一个 `alive`；返回 `loaded / project_keys / pcb_count / sch_count / probe_error / why` |
| `Client.open_project(..., verify_content=True)` | canary 之后再做内容探针；`loaded=false` 抛 **`OPEN_NOT_CONFIRMED`**，`next` 里写明"去窗口里点确认/取消"（桥内点不到） |
| `lceda_pro_verify` | 一次调用同时给三个事实，`connected` 只是第 3 条；失败码 `NOT_CONNECTED` / `NO_PROJECT_LOADED` |
| `lceda_pro_recover` / `desktop.launch` | 一个用户一个实例（见下） |

### 只留一个实例

实测现场：`tasklist` 有 7 个 `lceda-pro.exe`（Electron 主进程+渲染+GPU 的正常形态），
`Get-Process | ? MainWindowTitle` 只有 **1 个主窗口**。数进程数没有意义，**数窗口**才有。

事故成因：已经有一个实例在跑时，又用 `explorer.exe` 直接起了一次 —— 于是两个窗口共享
不了任何状态、抢同一个管道名，而且被驱动的那个悄悄换成了新的。

现在两处都不允许：

- `desktop.launch(exe, args, app=..., allow_second=False)`：`app` 已知且**已有带窗口的实例**
  → 直接回 `ALREADY_RUNNING`（带 `instances`、提示先复用或先关），进程根本不创建。
  `allow_second=true` 才是"我就是要两份"。
- `lceda_pro_recover`：`state != bridge_dead` 且已报出实例时回 `ALREADY_RUNNING`；
  只有 `bridge_dead`（管道在、永不应答）才是替换它的理由。

判据（能反向失败，`tests/test_lceda_live.py` 假 transport 覆盖）：有窗口 → 不 spawn；
`allow_second=true` → 照常 spawn；未知 `app` → 不设闸；`loaded=false` → `OPEN_NOT_CONFIRMED`
且 `ops == [ping, open, ping, invoke]`；`loaded=true` → 返回 sessionId 且 `last_open.content.loaded`。
